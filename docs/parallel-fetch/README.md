# 並列取得テスト

実測結果: [2026年10月24日の並列数の限界調査](capacity-investigation-20261024.md)。

`#parallel-fetch-test` で、同じランキングの連続した20または50ページを、指定した並列数で比較する。
並列数は1〜8の整数をカンマ区切りで入力し、比較基準の1を必ず含める。例は `1,3,5,8`。前後の空白を除き、小さい順に正規化する。重複・範囲外・1の欠落は入力エラーにする。`1` だけなら直列で連続取得を確認できる。
条件設定と実行状況を左右に置き、下に比較結果と各試行を表示する。狭い画面では縦に並べる。

## 起動と実行

`npm run dev` で起動し、ローカルURLの `/sf6/#parallel-fetch-test` を開く。
初期条件はLP、開始ページ1、20ページ、並列1と2、各1回、全タブ共通の取得開始間隔5秒と3秒。
取得開始間隔は秒をカンマ区切りで入力する。0〜60秒、0.1秒単位で最大3種類を指定でき、長い順に正規化する。0秒は間隔待ちなし。重複・範囲外・空要素は入力エラーにする。
適用範囲は「全タブ共通」と「タブごと」から選ぶ。1回のテストでは同じ範囲で間隔と並列数を比較する。
間隔ごとに並列数を比較し、初期条件では4条件・測定80ページ、準備を含め86回を予定する。実行順と予定取得数は開始前に表示する。
「取得開始」は、このPCに保存済みのBuckler認証状態を再利用して測定を始める。
接続状態と認証情報の保存有無は別表示であり、保存ファイルの存在だけでは認証の有効性を保証しない。
ログインが必要な場合は取得を停止する。既存の手動ログイン・セッション保存手順で更新してから再実行する。

実行APIはViteの開発サーバーだけに登録する。GitHub Pagesや `npm run preview` は結果JSONの読込・比較に対応し、取得処理を実行しない。
別ページへ移動してもサーバー上の測定は続く。「停止」または開発サーバーの終了で終了する。
同じ実行先で同時に開始できるテストは1件。全巡回や週次取得の設定は変更しない。

## GitHub Actionsでのテスト

実行先を「GitHub Actions」に切り替え、テスト内容を選ぶ。

| テスト | 対象 | 並列数 | 各試行 | 通常の読取回数 |
| --- | --- | --- | --- | --- |
| 取得間隔 × 並列数（初期条件） | LP 1〜20ページ | 1・2 | 間隔5秒・3秒で各1回 | 86回 |
| 直列確認 | LP 1〜20ページ | 1 | 3回 | 63回 |
| 並列比較 | LP 1〜20ページ | 1・2 | 1回 | 43回 |

通常の読取回数は事前確認を含み、再試行を含まない。「取得間隔 × 並列数」では0〜60秒の数値入力と適用範囲、並列数1〜8の整数（1必須）、繰り返し1回・3回を選択できる。ローカルと同じ入力検証と上限を使い、初期の並列数は `1,2` とする。既存の直列確認と並列比較は全タブ共通の5秒間隔を維持する。
ローカルのNode APIが、このPCのGitHub CLI (`gh`) の既存認証を使って、`gonchiman/sf6` の `parallel-fetch-test.yml` を `main` から起動する。GitHubトークンを画面に入力・保存しない。
Bucklerの認証は既存のActions Secret `BUCKLER_WEEKLY_SESSION` を取得ステップ内だけで使用する。ローカルの認証保存ファイルの有無はActionsの開始条件にはしない。

初回利用には、このワークフローと対応コードをmainへ取り込み、pushして登録する必要がある。未登録・無効のときは「ワークフロー未登録」として開始できない。
ワークフローは手動実行専用で、呼び出し元のリポジトリ・main・入力を検証し、dispatch時点のコミットSHAをcheckoutする。週次取得と共通のconcurrencyグループで、クラウド側の同時実行を避ける。

開始前にランダムな要求IDと選択条件をローカルへ保存し、Actionsの実行名 `Parallel fetch <要求ID>` と照合する。要求ID・run ID・attemptを組として管理し、最新の実行を推測して選ばない。結果の条件が保存した要求と一致することも検証する。
開始の通信結果が不明な場合は「受付確認中」とし、再確認では既存の要求を検索する。自動で再送信しない。
画面や開発サーバーを閉じてもクラウド実行は継続する。再起動後は保存した要求を再確認し、同じ実行の状態と結果を復元する。停止ボタンは特定できたrun IDだけにキャンセルを要求し、GitHubの確認後に停止扱いにする。

実行中は待機・準備・取得・結果読込の段階を表示し、未取得のページ進捗を推測して表示しない。
結果は実行に対応する単一JSON artifactだけを検証して取り込み、取得の失敗・ワークフローの失敗・結果未保存・保存期限切れ・読込失敗を区別する。途中で取得に失敗しても有効な部分結果があれば表示する。
artifactの保持期間は7日。取り込み後の結果と実行履歴は `.local/parallel-fetch-cloud/` に保存する。
「結果を再確認」は状態確認と結果取得だけを行い、新しい取得を開始しない。

比較表では選んだ1件の結果を表示する。実行先を切り替えても過去の結果の実行先は変わらず、ローカルとActionsの速度を混ぜて直列比を求めない。
新しい出力JSONは実行先とActionsの記録を含む封筒形式（`kind: parallel-fetch-result`）とし、従来の生の結果JSONも「実行先未記録」として読み込める。
静的配信ではローカルAPIへ接続せず、ActionsへのリンクとJSON入出力を利用する。

## 取得条件と上限

- LPは既存の総合・最大LPランキング、MRは今Act・最大MRランキングの固定条件を使用する。
- 条件ごとに専用タブを並列数だけ作り、各タブでページ1の認証・選択条件・表示構造を確認する。その後、全条件で同じ対象ページを新しく読み直す。
- 取得間隔の長い順、並列数の小さい順、繰り返し順に実行する。「全タブ共通」は全体で前回の取得開始から指定秒数を空け、「タブごと」は各タブの前回の取得開始から指定秒数を空ける。完了してから指定秒数を待つ方式ではない。同じタブの読取は重ねない。
- 取得開始は実際のページ遷移直前で計測する。事前確認・測定・再試行にも同じ適用範囲を使い、測定開始時に待ち時間をリセットしない。取得開始の予約を後からまとめて消化しない。
- 「タブごと」は新しいタブの初回取得を同時に開始できる。次の条件で作り直したタブの時計は新しくなり、「全タブ共通」の時計は条件を切り替えても引き継ぐ。
- 事前確認と再試行を含むページ読取上限は1テスト200回。ここでいう読取回数はページ遷移の開始回数であり、画像などを含めたHTTPリクエスト総数ではない。
- ローカル・Actionsとも全条件を通した取得処理を10分で中断する。開始間隔による最短の待ち時間だけで10分以上になる設定も、開始前に拒否する。待ち時間が10分未満でも通信時間などで上限に達することがある。
- 並列数の上限8は全経路の共通定義を使う。範囲内の並列数でも、ページ数・間隔・繰り返しとの組み合わせが読取回数または時間の上限を超える場合は開始できない。
- HTTP 5xxは全体の取得開始を5秒間停止し、同じページを1回だけ再試行する。待ち時間と再試行も測定・上限に含める。
- ログイン要求、認証確認不能、ロボット認証、HTTP 401/403/429、条件不一致、ページ形式変更などでは全タブを停止する。
- 停止や失敗した試行は部分結果として残し、完了にしない。

## 停止前後の診断記録

既存のDOM確認のたびに、認証表示・ログイン要求の見出し・ランキングの読取可否の変化を記録する。
ページ内の通信は、HTTP 4xx/5xxと通信失敗だけを記録する。記録するのは経過時間、観察段階、通信先の分類（Buckler・CAPCOM認証・その他）、リソースの種類、HTTPステータスだけ。URL、クエリ、ヘッダー、本文、任意のエラーメッセージは保存しない。

最初の `authentication-unconfirmed` では全ワーカーの取得を止め、処理が収束したあと、その失敗ページだけを最大30秒、5秒間隔で追加観察する。
同じ画面のDOMだけを読み、ページ遷移・再読み込み・追加の取得要求・スクロール・ログイン操作は行わない。ページ自身が継続する通信の失敗は記録する。
ログイン表示が戻っても取得を再開せず、元の失敗判定と成功ページ数を維持する。ロボット認証の検出・ページを観察できない状態・ユーザーによる停止では追加観察も終了する。その他の停止理由では30秒の追加観察を行わない。

追加記録は各attemptの `diagnostics.trace` に保存する。`observations` は表示状態、`network` は通信失敗、`postStop` は追加観察時間と終了理由を保持する。
各イベントの `elapsedMs` はそのページの読取開始からの経過時間で、attemptの `startedAt` と合わせて時刻を確認できる。段階は `read` と `after-stop` を区別する。
記録上限は表示・通信それぞれ80件。成功した読取と再試行対象のHTTP 5xxでは末尾8件ずつに絞り、除いた件数を保持する。追加観察時間は測定時間・ページ単位の取得時間に含めず、総時間に含める。
既存の結果JSONの入出力とActions artifactを使い、診断記録のない過去の結果も読み込める。

## 結果の定義

準備時間はタブ準備とページ1確認、測定時間は対象ページの取得開始待ちから最後の検証完了まで、総時間は後処理を含む時間。
成功ページ数は表示検証を通過した対象ページの数で、事前確認や再試行で重複計上しない。
速度は成功した対象ページ数÷測定時間。比較表は完了した試行の測定時間の中央値を使う。
比較表は間隔×並列数ごとに集計し、適用範囲を結果の取得条件に表示する。直列比は同じ適用範囲・取得間隔の並列1と比較先の予定試行がすべて完了したときだけ算出する。異なる間隔や適用範囲の速度を直列比の基準に混ぜない。
停止後の残りの条件は「未実行」として表示し、成功件数・失敗件数を0件と扱わない。開始済みでも予定した繰り返しが未完了なら「一部完了」として区別する。
失敗率は失敗した読取回数÷終了した読取回数で、準備と再試行も含む。未読取の場合は算出しない。

全巡回時間は、測定時に確認できた総ページ数と測定速度による参考概算。
長時間取得での速度維持・認証維持・同一時点の全件取得を保証する値ではない。
ランキングは取得中にも更新されるため、ページを全巡回しても同一時点の厳密な名簿にはならない。

## 保存と構成

終了時の結果を `.local/parallel-fetch/` に保存する。画面から結果JSONを保存・読み込みできる。
新しい結果は `schemaVersion: 3` で、`config.intervalScope`（`global` / `per-tab`）、選択した `config.intervalMsList` と各試行の `intervalMs` を保持する。固定モードは間隔リストを持たなくてもよい。従来形式（schema v1・v2）と適用範囲がない旧Actions履歴は「全タブ共通」として読み込める。新しい開始条件の時間上限を過去の結果へ再適用しない。結果を包む `parallel-fetch-result` の形式バージョンは従来どおり。
JSONは形式バージョン、固定した条件、時刻、所要時間、ページ番号、件数、HTTPステータス、固定の停止理由だけを保持する。
今回の読取で確認できた場合は、認証表示の種別、ログイン要求の有無、ランキング表示の読取可否も固定値として保存する。以前の結果JSONにこの項目がなくても読み込める。
認証情報、個別プレイヤーの名前・ID・一時ハッシュ、HTMLは結果に含めない。
保存済み認証状態は既存のDPAPIストアからNode側だけで読み、フロントエンドへ渡さない。
