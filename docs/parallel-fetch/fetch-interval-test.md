# 取得間隔テスト

`#fetch-interval-test` は、取得開始間隔だけを変えて比較するページ。比較条件と比較結果を縦に並べる。

## 固定条件と入力

- GitHub Actions、LPランキングの総合・最大LP、全地域・全プラットフォーム、1〜20ページ。
- 並列1（直列）、全体共通の開始間隔、各1回。
- 「最小間隔・最大間隔・刻み」を秒で指定する。初期値は最小5秒・最大10秒・刻み5秒（実行順は10秒 → 5秒）。
- 最小・最大は0〜60秒、刻みは0.1〜60秒、小数1桁まで。最小から刻みを足し、最大を超えない間隔を生成する。最大が刻みに一致しない場合は末尾へ追加しない（5〜10秒・2秒刻みなら9 → 7 → 5秒）。最小と最大が同じなら1条件。
- 既存の検証を使い、最大3条件を長い順に実行する。条件数超過・逆転した範囲・空欄・不正な刻みはエラーを表示し、送信しない。実行順と予定リクエスト数は入力時に確認できる。
- 10秒と5秒では測定40ページ、準備2回を含め42リクエスト。200回・10分の既存上限を維持する。
- 間隔は取得開始から次の取得開始までの最小時間。直列では前の取得完了も待つ。

ローカル画面の「比較を実行」は既存 `interval-compare` を呼び出す。Actions連携・受付記録・結果照合・停止条件は並列取得テストと共通。画面変更だけでは取得は開始しない。別の並列取得テストを含め、実行中・受付未確認・記録保存異常では重ねて開始できない。

GitHub PagesではActionsへのリンクと結果JSONの読込を使う。ブラウザーに認証情報を置かない。Actions artifactの裸JSONは実行先を証明できないので「実行先未記録」と表示する。既知のローカル実行、MR、並列2以上、各3回、タブごとの間隔、対象ページの異なる結果はこのページへ取り込まない。

## 結果

同じ固定条件に合う実行履歴から1件を選び、開始間隔・状態・成功ページ数・測定時間を表示する。入力中の次回条件と、保存済みの結果条件は分離する。

測定時間は20ページを完了した試行だけ表示する。途中停止は「未完了」、未着手は「未実行」、Actionsから記録が戻るまでは「待機中」「結果待ち」、結果がないまま終了した場合は「記録未取得」と区別する。件数未取得を0ページと表示しない。

詳細には停止箇所、成功した測定ページの読取時間中央値、準備時間、経過時間、停止理由、最後の取得のHTTP・認証表示・ランキング読取状況を表示する。準備取得と測定取得を分け、HTTP 200やログインボタンの観測だけから認証期限切れなどの原因を断定しない。

JSONは既存パーサーを使って検証・書き出す。上限は2 MB、取り込んだJSONの画面内履歴は20件。クラウドの実行履歴と取得済み結果は既存の `.local/parallel-fetch-cloud/` に保存される。

短いテストの完走だけで長時間の標本調査の安定性は判断しない。単一条件内の直列比はこの画面では表示しない。

## 再利用と検証

取得処理とworkflowは追加しない。`cloudConfig`、`useParallelFetchCloud`、入力・結果パーサー、`StatisticsPanel`、`table.css` を再利用する。範囲入力を整数ミリ秒で一覧に変換し、共通の間隔検証へ渡す。クラウド状態表示は既存ページと共有し、並列取得テスト側のカンマ入力は維持する。`arknights_2` のベンチマーク画面も参照し、条件の固定・実行記録と入力の分離を採用した。

`npm run test:parallel-fetch` で既存収集処理と新しい固定条件・集計の単体テストを実行する。UI確認はAPI応答を差し替え、実サイトへ取得を送信せず、開始条件、待機、途中停止、未実行、JSON読込、履歴切替、狭い画面を確認する。
