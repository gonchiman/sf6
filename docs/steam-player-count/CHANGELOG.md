# Steam取得処理の変更履歴

## 管理方法

- 起動役・取得・履歴保存を、共通の処理版 `v1`、`v2`、…で管理する。現在の版の定義元は [steamCollectionVersion.ts](../../src/lib/steamCollectionVersion.ts) の `STEAM_COLLECTION_VERSION`。画面と取得処理は同じ定義を使う。
- 画面内の変更履歴は、同ファイルの `STEAM_COLLECTION_HISTORY` で管理する。この文書と同じ版・コミット日時・実装コミットを保ち、変更時に両方を更新する。画面の「実装版」は同梱コードの版であり、稼働中の起動役や最新観測の取得版を示すものではない。
- 取得間隔、重複判定、再試行、引き継ぎ、取得対象、検証、保存、診断記録などを変更するときは、処理版を1つ進め、変更内容をこのファイルに追加する。同じコミットで版の定義と履歴を更新する。画面だけの修正や文書の誤字修正では進めない。
- 版は動作のまとまりを表し、コードを厳密に特定するには併記されたGitコミットSHAを使う。アプリ全体の `package.json` の版、Steam APIの `v1`、観測JSONの `schemaVersion` とは別に管理する。
- 各Actions jobは、checkoutしたコードの版・役割・SHAを、テストや外部取得の前にログとサマリーへ記録する。起動役の各イベントにも同じ情報を付ける。`node scripts/lib/steam-collection-version.ts --version` だけで版を確認でき、外部への取得は行わない。
- 起動役は開始時のコードを使い続け、取得・保存はそれぞれのrunのコードを使う。移行中は役割ごとに版やSHAが違う場合がある。mainへの反映日時と実際の稼働開始は区別し、適用済みかは該当jobの記録で確認する。
- 版名を付ける前のrunには版ログがない。以下の基準コミットと照合し、未確認の過去runを一律に `v1` と扱わない。ローカルで確認できないSHAは `null`／未確認と記録する。

## v2 — 2026-11-05

再確認・詳細ログの版。動作の変更は [832ba64](https://github.com/gonchiman/sf6/commit/832ba64dbe84027c7d5122946355bd1930e56563) でmainに統合。処理版の共通定義と実行時の記録は、その後の [cc9e486](https://github.com/gonchiman/sf6/commit/cc9e486a7610579fc3762b07247369c3cdf01e33) でmainに統合された。両者を初回の版管理対象 `v2` として整理しており、先行する再確認修正だけのrunには版記録がない。

- 過去スロットの取得が未完了に見える場合、5秒後に一度だけ実行詳細と最新一覧を再確認する。
- 同一run・attempt・作成時刻・更新時刻を照合し、完了を確認できた場合に取得を開始する。新しいrunや再実行がある場合は見送る。
- 失敗箇所、HTTP番号、エラー分類、スキップ理由、実行状態を記録する。
- 再確認にも60秒の起動猶予と起動役全体の時間制限を適用する。起動POSTの再送は追加しない。
- 共通の処理版を定義し、起動・取得・履歴保存のActionsログとサマリーに版・役割・SHAを記録する。
- 取得間隔は引き続き15分、対象は5ゲーム。

## v1 — 2026-11-02：自動引き継ぎを追加

機能の導入コミットは [528819d](https://github.com/gonchiman/sf6/commit/528819d55051361b998f4e9621ccafbc487ca459)。既存の比較用基準コミット [aee168f](https://github.com/gonchiman/sf6/commit/aee168f1b3c0ca0831cd3223d7490f3eb90b7181) までに、取得・起動・履歴保存のスクリプトとworkflowの追加変更はない。`v1` は2026-11-05に後付けした名称。

- 毎時07・22・37・52分に取得を起動し、5ゲームの現在値を取得・保存する。
- 起動役は最大330分動き、終了時に待機中の後続を確認する。後続がなければ自身で1回だけ起動を要求し、予約を確認する。毎時cronは復旧用として残す。
- 引き継ぎの確認は別枠で最大120秒。起動要求の応答が不明でもPOSTを再送せず、run一覧で予約を確認する。
- 親runのID・attemptと引き継ぎ確認stepを照合してから後続を開始する。無効化やキャンセルされた処理を後続で再開しない。
- 2分で交代を検証する `handoff-check` を追加。後続は通常の330分モードへ戻す。
- 最新の取得が未完了と返された場合は、そのスロットを見送る。実行詳細を使った5秒後の再確認は行わない。
- スキップ・失敗の基本イベントは記録するが、v2の詳細な判定情報と処理版の記録は持たない。

## v0.3 — 2026-11-02：5ゲーム対応

根拠: [6fe802d](https://github.com/gonchiman/sf6/commit/6fe802d2050bbfcbf901104b5775f57361f1b80f)。

- SF6に鉄拳8、GUILTY GEAR -STRIVE-、グランブルーファンタジーヴァーサス -ライジング-、THE KING OF FIGHTERS XVを追加。ゲーム定義を共通化し、同じ取得runで順番に取得する。
- ゲームごとの成功・失敗を持つ `batch.json` を導入。一部失敗でも成功分を保存し、全ゲーム失敗時は履歴を書き換えない。失敗分の人数を0で補わない。
- サーバーから長い待機を要求された場合や429の再試行を使い切った場合は、同じホストに対する残りのゲーム取得も見送る。
- SF6の既存保存先を維持し、追加ゲームは別ディレクトリへ保存する。成功分を一度の履歴コミットにまとめ、新しいゲームだけ初期履歴を補う。
- 取得jobの上限を5分から10分へ変更。起動役の15分間隔は維持する。

## v0.2 — 2026-11-01：15分タイマーを導入

根拠: [dd50d56](https://github.com/gonchiman/sf6/commit/dd50d5672e483747c88a1e8d7cf258b1e7b33fd8)。

- 取得workflow自身の15分cronを外し、別の起動役が毎時07・22・37・52分に取得を要求する構成へ変更する。
- 起動役は最大330分・22回の起動要求に制限。毎時11分のcronで後続の起動役を補充する。この時点では自己引き継ぎはなく、次の起動役をcronに依存する。
- 動作中の起動役は1つ、待機は最大1つにする。新しいcronで動作中の起動役を中断しない。
- 同じ時間枠の取得や未完了runがあれば重複起動しない。60秒を超える遅れは見送り、過去の枠をまとめて取り直さない。
- workflowの無効化を最大約60秒間隔で確認し、認証・権限エラーやレート制限では停止する。起動POSTの成否が不明な場合は、その枠で再送しない。

## v0.1 — 2026-10-31：SF6の取得・履歴保存を追加

根拠: [14b0e36](https://github.com/gonchiman/sf6/commit/14b0e36eafffa80adf2c0fabcdca6c07705354e8)。

- Steamの公開APIからSF6の現在の同時接続数を1件取得する処理と、取得・履歴保存を分けたActions workflowを追加する。最初の対象はSF6のみ。
- 取得workflowを毎時07・22・37・52分のcronまたは手動操作で起動する設定を追加する。cronの設定自体は、15分ごとの実行成功を保証しない。
- 応答を検証し、実際の要求開始・応答完了時刻とrun ID・attemptを記録する。一時的な通信障害や対象HTTPエラーは合計最大3回まで試し、長い待機要求では終了する。
- UTCの日別JSONとハッシュ付き一覧を専用の履歴ブランチへ保存する。公開のpushが拒否された場合は最新履歴へ同じ観測を再反映し、合計最大3回まで試す。
- 公開jobだけの再実行でも元の取得artifactを参照できるよう、artifact名を取得jobから受け渡す。同じ観測の再反映で履歴が重複しないようにする。
