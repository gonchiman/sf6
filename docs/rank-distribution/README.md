# ランク分布の取得・公開仕様

週次取得の全体像と現在の進捗は[ランク分布の週次取得フロー](weekly-collection-flow.md)を参照。
クラウドでの先頭ページ・分布全体の単発取得の手順と実証結果は[クラウド取得検証](cloud-probe.md)を参照。
保存済み認証で全ランクの取得を試し、検証できた集計をローカルアプリへ取り込む手順は[ランク分布の取得とアプリへの取り込み](collection.md)を参照。

同じページの「MR帯」で表示する今Act・最大MRの100MR刻みの分布は、[MR分布の仕様と取得手順](mr-distribution.md)を参照。以下はLPランク分布の仕様。

## 画面の構成

条件選択、縦棒グラフ、数値の表を上から順に配置する。取得日欄は常時表示し、保存済みデータが1件ならその取得日時、0件なら「未取得」を表示して選択不可にする。複数件では保存済みの取得日から選択でき、初期値は最新とする。グラフの見出しに掲載総数を添え、取得期間・短い概数の注記・出典は折り畳まず確認できるようにする。

開始時の総数・観測範囲・詳しい集計方法や検証記録は、表の下の「集計方法・取得情報」へまとめ、初期状態では閉じる。★別でも割合・累積割合の分母は全体とし、取得失敗や読み込み失敗は折り畳まず表示する。パネル、表の罫線、補足の開閉には既存の共通部品・スタイルを使う。

### 分布のグラフ

グラフと表は同じ取得日・表示区分の集計行を共有し、ランクの低い順に並べる。グラフの初期値は全体比（%）で、アカウント数（件）に切り替えられる。★別も掲載アカウント全体を分母とし、累積割合は表へ残す。棒は既存の変更項目数グラフと同じ中立グレー、軸は常に0起点とし、表示範囲は有効な値をすべて含む。

数値は丸め前の値で描画し、棒の上とツールチップには表示用の丸めを使う。狭い画面でも縦棒を維持し、ランク名や数値が重ならないように調整する。未取得・読込失敗にはグラフを表示せず、確認済み0件はゼロとして示す。総数0件の割合は算出不可として棒を描かない。取得日を切り替えた際は、前の取得日のグラフも表示しない。

## 集計単位

対象は、BucklerのLPランキングを「リーグ：総合」「キャラクター：最大LP」「地域・プラットフォーム：すべて」の固定URL条件で表示した一覧の登録ファイターアカウント。ランク別件数を合算し、その総件数を割合の分母にする。`user_status=1`は固定条件として保持するが、可視選択欄との対応が未確認なので「全ユーザー」とは解釈しない。

- 同じアカウントが使う複数キャラクターの件数と、アカウント件数を混ぜない。
- SteamとPS5等で別のファイターアカウントを持つ同じ人を、公開ランキングから統合した実人数ではない。CAPCOM IDの連携とランキングのユーザーコードを区別する。
- 直近のランクマッチ参加人数ではない。最終プレイ日時だけから、ランクマッチの活動期間を確定しない。
- 最大LPのキャラクターに基づく掲載ランクを使う。過去最高到達ランク、現在主に使うキャラクターのランク、MRの分布とは別の指標。
- ID 1〜35はROOKIE〜DIAMONDの各★1〜5、36はMASTER。Legend等のMR区分を別に加算しない。

出典は[公式LPランキング](https://www.streetfighter.com/6/buckler/ja-jp/ranking/league)。ファイターアカウントは[公式マニュアル](https://game.capcom.com/manual/SF6/en/ps5/page/1/1)の定義を参照する。[CAPCOM IDのFAQ](https://cid.capcom.com/ja/support/)は、異なる種類のプラットフォームアカウントを同じCAPCOM IDへ連携できると説明している。

## 境界探索ヘルパー

[`scripts/lib/rank-distribution-boundaries.ts`](../../scripts/lib/rank-distribution-boundaries.ts)は、読み取り関数`fetchPage(page, url)`を注入する純粋な集計処理。ネットワーク取得、認証、DOM操作は別処理に分け、全件取得への切り替えは行わない。実画面のアダプターと保存済み認証を接続するCLIは[`scripts/collect-rank-distribution.ts`](../../scripts/collect-rank-distribution.ts)。

固定条件URLは以下。ページ番号だけを差し替え、他の条件を追加・変更しない。

```text
https://www.streetfighter.com/6/buckler/ja-jp/ranking/league?character_filter=2&character_id=luke&platform=1&user_status=1&home_filter=1&home_category_id=0&home_id=0&league_rank=0
```

`character_id=luke`は確認済みの最大LP条件URLに残る値。特定キャラクターを対象にした集計へ変更しない。フィルターの値・名前が変わった場合は、現行UIで確認し、ヘルパーを更新してから使う。

アダプターが返す`RankBoundaryPage`：

| 項目 | 入力仕様 |
| --- | --- |
| `sourceUrl` | 実際に表示・確認した公式ページURL。要求した`page`を含み、固定条件と一致すること |
| `page` | 読み込まれた一覧のページ番号。要求番号をそのまま代入して到達の証拠にしない |
| `pageSize` | 現行の通常ページ件数。20件という過去の観測を未確認の既定値にしない |
| `totalCount`, `totalPages` | そのページで確認した総件数・総ページ数 |
| `entries` | 表示順の`{ leaguePoint, rankId, accountKey? }[]`。LPは整数、ランクは1〜36 |
| `accountKey` | 重複検査用の任意の安定した私的キー。ヘルパー出力・公開データへは含めない |

通常画面の公式ランク画像IDを独立に読み取れる場合は、`mode: 'rank-id'`でランクIDそのものを比較する。現行のLP閾値表を仮定せず、公式画像IDとリーグ選択肢の表示名の対応を確認し、LPとランクの両方の降順を検査する。

LP閾値を使う従来方式（指定なし、または`mode: 'league-point'`）では、境界`ranks: { rankId, minimumLp }[]`を36区分すべて呼び出し側から渡す。古いLP表の既定値は持たず、現行の表示との対応を確認する。どちらの方式も、未ランク、読み込みプレースホルダー、不明なリーグ画像をROOKIEや0件に変換しない。

手順は、先頭・末尾を確認し、各ランク以上となる範囲の終端を二分探索する。ランクID方式では表示ID、LP方式では確認済みの最低LPと比較する。隣接する境界位置の差から各区分の件数を計算する。位置は`(page - 1) × pageSize + 行の位置`を使い、同LPで同順位になり得る表示順位の差を人数として使わない。境界の前後と先頭・末尾を別の読み取りで再確認する。

ヘルパーは以下を拒否する。

- 固定条件からの変更、要求ページへの未到達、ページ数・件数・末尾件数の不一致。
- LP順の逆転、LPとランクIDの不一致、観測したキーの重複・位置変化。
- 取得中の総件数変更、再確認時のページ内容変更、取得失敗・メンテナンス。
- 取得回数上限または中止。キャッシュを再確認の別観測として数えない。

ヘルパー成功時の`observedChecks`は確認した範囲の検査結果であり、配信可能な`verified`データセットではない。特に`max-lp-account-unit-confirmed`と`unranked-tail-confirmed`を自動付与しない。一部ページで重複がなかったことだけから全件の一意性を証明しない。

## 保存する形式と取り込み前の検証

配信データは[`RankDistributionDataset`](../../src/types/rankDistribution.ts)に従う。既定の概数方式と、従来の観測内容の一致を要求する方式を区別する。各確認の根拠を`validation.notes`へ記録する。確認コードを書いただけで、未取得の境界や部分取得を完成したデータと扱わない。

概数方式は`method: boundary-search-estimate`、`validation.status: estimated`、`coverage: all-rank-boundaries`とする。次表の`total-count-stable`は要求せず、代わりに`changes-recorded`と`observation`を必須とする。他の確認項目は維持するが、順序確認は各ページと境界の前後を対象とし、異なる時刻の同一行・LP・個人位置の一致は要求しない。

`observation`の`totalAtStart`・`totalAtEnd`・`minTotal`・`maxTotal`は実観測総数。`boundaries`にはID 2〜36の全35境界について、`rankId`・`countAtOrAbove`・`totalCount`・`observedAt`を保存する。全時刻は取得期間内、累積件数は観測総数以下でランク上昇に対して非増加、終了時総数と36区分の件数・逆累積が整合することを検証する。総数の変動や境界の観測時刻の違いは誤差上限を意味しない。画面では取得期間中の概数と表示する。

従来方式は`method: boundary-search`、`validation.status: verified`、`coverage: all-listed-accounts`で、次の9項目をすべて要求する。概数方式の観測記録やチェックをこの形式へ混ぜない。概数方式の詳細は[取得手順](collection.md#概数の定義)を参照。

| 確認コード | 必要な確認 |
| --- | --- |
| `conditions-confirmed` | 可視選択欄の総合・最大LP・全地域・全プラットフォームと、`user_status=1`を含む固定URLが一致する一覧。パラメーターの意味を全ユーザーと断定しない |
| `pagination-confirmed` | ページ番号・通常ページ件数・総ページ数・総件数の整合と深いページへの正常到達 |
| `final-page-confirmed` | 最終ページが表示でき、末尾の件数が総件数と一致 |
| `ordering-confirmed` | LP降順とページ間の順序。同LPの行を取り落とさない |
| `rank-mapping-confirmed` | 現行の公式ランクID・表示名の対応。LP比較方式では独立に確認したLP閾値も必要 |
| `max-lp-account-unit-confirmed` | アカウント単位に最高LPのキャラクターが掲載される集計定義の根拠 |
| `total-count-stable` | 取得期間内のすべての観測で総件数・ページ構成が一致 |
| `boundaries-rechecked` | 境界の前後を新しい読み取りで再確認して一致 |
| `unranked-tail-confirmed` | 未ランク・不明区分の扱いを確認し、欠損の補完を行っていない |

LPランキングには取得月の選択がないため、データを月次統計として遡って復元しない。`captureStartedAt`と`captureEndedAt`を持つ取得期間の観測として保存する。開始・終了で総件数が一致しても、その間のランク移動を排除した原子的なスナップショットとは主張しない。

どちらの方式も、一部の境界だけ確認できた結果を36区分が揃った集計として登録しない。境界の中間位置を正確な件数にしたり、根拠のない信頼区間を付けたりしない。失敗時は前回正常値を保持し、一覧の`availability`へ取得状態・確認日時・理由を残す。全件取得へ自動で切り替えない。

## ページへの自動反映

LPランク分布は、公開ブランチ`codex/rank-distribution-history`の`data/index.json`と日付付き集計JSONをGitHub Rawから読み込む。週次保存後の通常の閲覧に手動importは不要。

- ページを開いたとき、表示中の5分ごと、非表示のタブから戻ったときに一覧を再確認する。最新の取得日を表示中なら新しい集計へ切り替え、過去の日付を選んでいる場合は選択を維持する。表示区分と棒の値の選択も維持する。
- 一覧と本体を同じ配信元から読み、既存parserで36区分の件数合計・取得条件・取得区間・概数の検証結果を確認する。新しい本体の検証が済むまで、表示中の正常データを置き換えない。
- 初回に履歴一覧または最新の本体を読み込めない場合は、`public/data/rank-distribution/`の同梱データへ切り替え、その状態を表示する。表示中の通信失敗や履歴の欠落・後退では正常表示を維持する。自動再確認と「更新を再確認」で再試行できる。
- 一覧の`generatedAt`は生成日時であり、最新取得日は`captureEndedAt`で判定する。週次処理が失敗して新しい正常集計が追加されなければ、過去の正常集計を表示する。現在の週次処理の失敗理由は`runs/`に保存されるため、一覧を読めたことを最新の収集成功とは扱わない。
- ページが読むのは公開済みの集計JSONだけ。Bucklerへの新規取得、認証情報の読込、部分取得の公開は行わない。
- ローカル開発画面とGitHub Pagesで共通。GitHub Pagesでは、この変更をmainへ反映して一度デプロイした後は、集計履歴の追加だけで表示を更新できる。GitHubのキャッシュや通信状況により反映が遅れる場合がある。

レジェンド帯分析の読み込み・更新処理を`publishedDataFeed`、`publishedDataRefresh`と共通Hookへ分離して再利用する。MR帯も同じ仕組みで専用の公開履歴を読む。MRの取得条件・単発検証・週次実行の有効化は[MR分布の仕様](mr-distribution.md#クラウド取得とページへの自動反映)を参照。

## JSONの取り込み・検証

週次実行・集計履歴の保存・7日後の認証再利用の判定は[週次取得の運用](weekly-collection.md)を参照。

[`scripts/import-rank-distribution-data.ts`](../../scripts/import-rank-distribution-data.ts)は、単一の概数・従来方式の完成データセット、同形式JSONだけを置いたフォルダー、または`{ schemaVersion: 1, datasets: [...] }`というバンドルを取り込む。入力は必須で、確認済みの取得データがない状態を人工の0件集計で埋めない。

```powershell
npm run data:import-rank-distribution -- .cache/rank-distribution/verified-capture.json
node scripts/validate-rank-distribution-data.ts
```

入力バッチ全体を検証し、排他ロックを取得して、既存一覧を検証、作業先へステージング、ステージ全体を再検証した後に入れ替える。失敗時は既存データを復旧する。同じ取得開始・終了の記録だけを置き換え、他の取得記録は保持する。

36区分の不足、重複、件数合計の不一致、未検証・部分取得、日時の矛盾、個人情報等の未知キー、パストラバーサル、Windows予約名、リンク、未登録ファイルは拒否する。取り込みが成功すると過去の取得失敗表示を解除する。画面へ配信するJSONには集計値・取得条件・出典・期間・検証結果だけを含める。

既存の勝率スナップショット、使用率のimport/validation、勝率のステージング・復旧方式を参照し、ランク分布の厳密な条件と個人情報の検査を追加した。境界処理・欠損・同LP・更新中の変化・条件リセットと、無効バッチで既存ファイルが変わらないことを人工データのテストで確認する。人工テスト値は実データとして配信しない。
