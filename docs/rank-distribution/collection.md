# ランク分布の取得とアプリへの取り込み

保存済みの認証でBucklerの通常ランキング画面を読み、全ランクの境界が確認できた場合だけ集計JSONを保存し、ローカルアプリへ取り込む。既定では、更新されるランキングを取得期間中の「概数」として扱う。表示には既存のランク分布ページを使う。

## 実行

このPCの同じWindowsユーザーで、ローカル認証の保存を済ませてから実行する。

```powershell
npm run data:collect-rank-distribution -- --collect
```

既定では新しい表示付きEdgeで、総合・最大LP・全地域・全プラットフォームの固定条件の掲載一覧を読む。認証をクラウドへ送らず、CAPCOM IDへの自動ログインやロボット確認の操作も行わない。ログイン状態を復元できなければ取得を止める。

取得回数は既定600回、最大1000回で制限する。概数方式ではページの読み取り開始を5秒以上空け、同時に複数のページを要求しない。必要な場合だけ上限を指定する。

探索済みページの全行を全ランクの境界探索に共有し、先頭・末尾から確定する範囲は追加探索しない。全36ランクが存在する仮想3,060,715件のテストでは、従来の495回から448回へ読み取りを削減し、同じ件数と全境界の再確認を維持した。この人工データでの改善は、実取得の成功や時間短縮率を保証しない。

```powershell
npm run data:collect-rank-distribution -- --collect --max-requests 600
```

中止はCtrl+C。全件走査や無制限の再試行へ自動で切り替えない。週次実行とクラウドでの分布全体の取得は、このコマンドとは別に設定・検証する。

タイムアウト、通常の読み取り失敗、ログイン表示の確認待ちが完了しない場合、HTTP 5xxのサーバーエラーに限り、同じページを1回だけ読み直す。5xxの場合は5秒待ち、実際に行った再読も取得回数の上限に含める。アクセス拒否（401・403・429）、明確なログイン要求、404等の他のHTTPエラー、メンテナンス、不明ランク、条件変更では再試行しない。レポートには再読回数・固定の最終失敗コード・最後のHTTPステータスを残し、認証が必要な表示と、認証状態を確認できなかった状態を区別する。

概数方式の時間上限は60分。従来の総数・観測内容の一致を要求する方式も、`--strict`で選べる。この方式の時間上限は15分。

概数方式では20分ごとに、このコマンドが開いた取得用Edgeだけを閉じ、実行開始時に読み込んだ同じ保存済み認証状態で新しいEdgeを開く。新しい先頭ページでログイン状態・固定条件・ランク表示・ページサイズを確認できた場合だけ、それまでの境界探索を続ける。認証情報を再保存せず、取得期間・全体の時間上限・読み取り回数をリセットしない。追加の先頭確認も回数と総数の変動記録に含め、成功した開き直しの回数をレポートの`sessionRefreshCount`へ記録する。

新しいEdgeでログイン要求・アクセス拒否が出た場合や、前の取得用Edgeを閉じられない場合は停止する。CAPCOM IDのログインやロボット確認を繰り返す処理ではない。従来方式ではブラウザーの開き直しを行わない。

```powershell
npm run data:collect-rank-distribution -- --collect --strict
```

## 途中保存と再開

概数方式では、境界を確認するたびに、Git管理対象外の`.local/rank-distribution/checkpoint.json`へ探索位置を保存する。停止後は同じWindowsユーザーで次を実行する。

```powershell
npm run data:collect-rank-distribution -- --collect --resume
```

保存するのは形式の版、固定条件URL、ページサイズ、保存日時と、各境界のランクID・行位置・観測総数・観測日時だけ。行データ、個人名、ID、LP、認証情報は含めない。既存の保存方式を参考に、排他ロックと一時ファイルからの置換で最後の正常ファイルを保持し、別の取得で保存した探索位置もランクごとの新しい観測を優先して保持する。

再開時は保存した位置がないランクから先に探索する。過去の位置は候補として使い、保存済みのランクも新しい前後行で確認し直す。今回の先頭・末尾と全35境界が揃うまでは完成データとして保存・表示しない。取得開始日時と総数の範囲も今回の実行で新しく記録し、停止前の観測を今回確認済みの人数に流用しない。

保存ファイルがない、壊れている、固定条件やページサイズが異なる、未来の時刻を含む、保存先がリンクになっている等の場合は、再開せず理由を記録する。従来方式の`--strict`と`--resume`は併用しない。ログイン要求やアクセス拒否が出たらその実行は停止し、CAPCOM IDへの自動ログインや認証チャレンジの突破は行わない。

## 概数の定義

同じランク内の順位やLPの変化、掲載総数の増減だけでは止めず、全35境界の前後を新しい読み取りで確かめる。探索済みページは候補の絞り込みに使い、古い観測を境界の再確認として扱わない。境界が動いた場合は取得回数を制限して近傍を探し直し、確認できなければ保存しない。

境界ごとの「そのランク以上」の行位置の差から36区分の概数を計算し、終了時に観測した掲載総数を割合の分母にする。異なる時刻の境界位置から求めるため、同一瞬間の正確な人数を表さない。件数合計と総数が一致することも、この計算の整合確認であり、同時点の人口を証明するものではない。

データ形式は`method: boundary-search-estimate`、`validation.status: estimated`、`validation.coverage: all-rank-boundaries`。`observation`には開始・終了・観測中の最小最大総数と、ランクID 2〜36の35境界の行位置・観測総数・確認時刻を保存する。`total-count-stable`の代わりに`changes-recorded`を要求し、検証済みの従来方式とは区別する。事前確認を含む総数範囲は取得レポートにも残す。

総数の変化はランク別人数の誤差上限ではなく、同じ総数のままランクが移動する場合もある。総数差から信頼区間や「誤差は数人」といった数値を作らない。画面では件数・割合を概数として表示し、取得期間と観測した総数の変化を確認できるようにする。

## 画面から確認する項目

公式画面のリーグ選択肢には、総合のID 0、Rookie1〜Diamond5のID 1〜35、MasterのID 36がある。行末のランク画像は通常のスクロールで読み込み、公式の`rank1_l.png`〜`rank36_l.png`からランクIDを独立に読む。個人名やIDからランクを推測しない。

直接ランクIDを比較する境界探索では、未確認のLP閾値表を使わない。LPの降順とランクIDの降順を検査し、各ランク以上の行位置を二分探索する。境界位置の差から人数を求め、全35境界の前後・先頭・末尾を新たに読み直す。

表示ページの選択欄、URL、件数範囲、行数、読み込まれたランク画像を照合する。ページ選択肢は10ページごとの窓であり、その最後の値を総ページ数と誤認しない。最終ページは、先頭で実測したページサイズと総数から計算し、実際の最終ページの表示で確かめる。

地域・プラットフォーム等の画面上の条件を確認する。`user_status=1`は固定URLとの一致を検査する。公式画面の通常のフィルター設定から同じ値が生成されることは確認したが、専用の可視選択欄との対応は未確認で、「全ユーザー」を意味するとは断定しない。JSONの`conditions.users`にも意味を推測しない`buckler-user-status-1`を使う。

## 成功したとき

36区分が揃い、取得条件・各ページの件数範囲・全35境界が確認でき、負の件数や境界の逆転がなく、必要な確認根拠が揃った場合だけ集計JSONを検証する。従来方式では総数と再取得したページ内容の一致も要求する。

集計値は取得日時とともにGit管理対象外の`.local/rank-distribution/`へ保存し、既存の取り込み処理で`public/data/rank-distribution/`へ反映する。アプリの`#rank-distribution`で取得日、ランク帯ごと・★別の人数、割合、累積割合、出典、取得期間を確認できる。

保存するのは集計値と検証情報。アカウントの重複・位置確認に用いるsalt付きハッシュは取得中のメモリ内だけで扱い、集計JSON・取得状況・ログへ含めない。認証情報、個人名、生ID、HTML、通信記録、画面画像も出力しない。

## 取得を止める条件

概数方式でも、取得条件の変更、到達ページやページ内の件数範囲の不整合、未知のランク画像、ページ内の順序・重複の矛盾、境界の未確認や逆転、負の件数、アクセス拒否、メンテナンス、認証未確認、時間切れ、回数上限、中止があれば登録しない。従来方式では取得中の総数・ページ構成・再取得したページ内容の変化も停止条件とする。

前回の正常な集計と履歴は保持し、アプリには新しい確認日時と固定の理由を表示する。未取得・一部だけの取得・失敗を全ランク0件として埋めない。取得期間中の整合を確認できた場合でも、単一時点の原子的な人口スナップショットとは扱わない。

## 実画面での確認記録

2026年10月15日に、固定条件の先頭と最終ページへ到達し、先頭のMASTER画像と末尾のROOKIE★1画像を確認した。末尾は0LPだったが、LP値から分類したのではなく、読み込まれた公式画像のID 1と選択肢Rookie1の対応を確認した。

総数は別々の診断で3,060,681〜3,060,687件へ変化していた。これらの診断は分布全体の完全集計ではない。

同日16:39:37〜16:41:29（日本時間）に、取得コマンドで分布全体の取得を1回試した。保存済み認証を再利用し、手動ログインなしで先頭・最終ページを読めた。開始時の総数は3,060,715件、ページサイズ20件。19回目の読み取りで総数の変化を検知して停止し、成功した読み取りは18回だった。分布全体の検証には到達していない。

この実行では完全集計JSONを作らず、アプリの取得状況を`collection-failed`へ更新した。新しく開いたEdgeは終了し、認証や個別行を含まない診断だけをGit管理対象外の`.local/rank-distribution/capture-2026-10-15T07-39-37-593Z.json`へ保存した。実画面でも16:41 JSTの停止理由が表示され、架空の0件表が出ないことを確認した。

この実行は従来の厳密な方式であり、読み取り中の更新が完全集計の妨げになった。その後、ユーザーが取得期間中の概数として扱う方針を選択したため、全35境界の確認と変動記録を要求する概数方式を追加した。未取得の境界や途中の値は完成値として採用しない。クラウドでの分布全体の取得、週次設定、1週間後の認証再利用は別途検証する。

同日17:31:46〜18:01:47 JSTの概数取得では、350回の読み取りのうち349回が成功し、全35境界のうち23境界を確認した。観測総数は3,060,822〜3,060,884件で、この変動では停止しなかった。開始から約30分後、HTTP 200の画面に明確なログイン要求が出たため停止した。未確認の境界が残るため、集計データは登録していない。

その後、同じ元の保存済み認証状態を新しい取得用Edgeで再利用すると、先頭・最終・深いページをHTTP 200で読めた。元の保存済み認証が全体として期限切れになったとは判断せず、上記の20分ごとの開き直しと新しい先頭ページの確認を追加した。

同日18:10:24〜18:20:28 JSTに再実行したが、111回目にHTTP 200の画面で明確なログイン要求が出て停止した。110回は成功し、7／35境界まで確認、観測総数は3,060,902〜3,060,934件だった。今回は約10分で停止し、`sessionRefreshCount`は0。20分ごとの開き直しには到達しておらず、その対処の実環境での有効性は未確認である。前回の約30分という経過時間を認証の固定有効時間とは扱わない。

最新の診断は`.local/rank-distribution/capture-2026-10-15T09-10-24-535Z.json`へ保存した。取得用Edgeを終了し、アプリの取得状況を18:20 JSTのログイン要求へ更新した。完成した集計JSONは作成・登録していない。概数の処理・保存形式・UIを含む人工データでの回帰テスト545件は成功したが、全体の実取得成功や週次運用の実証とは区別する。
