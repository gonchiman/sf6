# ランク分布の日次取得フロー

更新日: 2026年10月28日

自分のPCがオフでも毎日19:30 JSTからBucklerのLP分布を取得・保存し、成功後にMR分布を取得・保存する。ランク分布ページはそれぞれの保存済み集計を自動で読み込む。過去の取得日も選択できる。ローカル開発画面とGitHub Pagesで同じ読み込み処理を使う。

このPCで認証状態を暗号化保存し、ツールとEdgeを終了した後の別起動で再利用できた。さらに2026年10月15日21:55:47〜22:15:49 JSTには、[GitHubのWindows環境で分布全体の取得に成功](https://github.com/gonchiman/sf6/actions/runs/38738293951)した。保存済み認証を使って手動ログインなしに全35境界を新しく確認し、1データセット・36区分を保存した。件数の合計と終了時総数は3,061,539件で、ローカルへの手動取り込みも完了した。

2026年10月16日、ユーザーの明示許可を受けて週次workflowを有効化し、週次専用Secretを継続保管する設定を行った。最初の手動確認2回はHTTP 503で停止したが、[その後の再確認](https://github.com/gonchiman/sf6/actions/runs/38861770850)では同じ保存済み認証を使って取得job・保存jobとも成功した。手動ログインなしで全35境界を新しく確認し、新規36区分の集計を保存できた。初回の定期実行予定は2026年10月22日（木）22:30 JSTだった。その後10月23日のrunで定期起動と7日後の認証再利用を確認した。

## 設定した取得フロー

```mermaid
flowchart TD
    A["毎日19:30 JSTにクラウドで起動"] --> B["保存したログイン状態でBucklerを開く"]
    B --> C["LP分布を取得"]
    C --> D["LP集計を取得日ごとに保存"]
    D --> E["ページが保存済み集計を自動表示"]
    D -->|"取得・保存とも成功しMRが有効"| H["MR分布を取得・保存"]
    H --> E
    B -. "認証が切れていたら" .-> F["自分で手動ログイン"]
    F --> G["保存する認証状態を更新"]
    G --> B
```

初回は手動でログインし、次回以降に使う認証状態を安全に保存する。通常の取得は自動で行い、認証の期限切れ時には手動で更新する。単発検証用Secretは削除済みで、現在は別の週次専用Secretを継続保管している。日次設定への変更後も、認証の有効期間と定期実行の動作は実際の実行結果で確かめる。

取得時は自分のPCの起動を不要にする。保存された結果をローカルアプリで閲覧するときは、PCとアプリを起動する。

## 保存するデータと失敗時の扱い

履歴として保存するのは取得日時、取得条件、ランク別のアカウント件数、出典、検証結果。ユーザーが選択した概数方式では、全35境界の位置・確認時刻・観測総数、取得期間全体の開始・終了・最小最大総数も保存する。割合は終了時総数を分母に表示時に計算し、同一時点の人口や総数差に基づく誤差上限とは扱わない。

今回クラウドで新しく観測した35件の探索位置も、ローカルの固定checkpointへ安全にマージ済み。次回取得の候補として使い、過去の境界を完成値として持ち越さない。

対象は総合・最大LP・全地域・全プラットフォームの固定条件で掲載されたランキングで、集計単位はファイターアカウントとする。`user_status=1`は固定条件として記録し、全ユーザーという意味は未確認として扱う。

認証情報は集計結果と分けて管理する。元のDPAPI保存と専用ブラウザープロファイルはこのPC内に保持する。10月15日のクラウド単発検証で使った`BUCKLER_CLOUD_PROBE_SESSION`とそのreceiptは削除済み。10月16日は別途の明示許可を受けて、Street Fighterサイト用の認証状態を`BUCKLER_WEEKLY_SESSION`へ送信した。週次用Secretは運用停止または認証更新まで継続保管する。DPAPIファイル自体や専用プロファイル全体はクラウドへ送っていない。

保存するのは集計・探索候補・安全なrun記録だけで、専用ブランチ`codex/rank-distribution-history`に保存する。LPランク分布ページは同ブランチの集計JSONを直接読み、表示中に再確認する。この自動反映の実装を一度mainへ反映・公開した後は、集計更新のたびにmainへデータを取り込む必要はない。詳細は[ページへの自動反映](README.md#ページへの自動反映)を参照。

取得に失敗した日は前回の正常データを保持し、失敗を記録する。LP失敗時は後続MRも見送る。未取得や一部だけの取得を、全ランク0件や完全集計として保存しない。取得条件と検証の詳細は[ランク分布の取得仕様](README.md)に従う。

## 日次運用の実装

既存の認証Secret・データ保存・ページ反映を使い、LPの起動を毎日19:30 JSTへ変更した。[日次workflow](https://github.com/gonchiman/sf6/actions/workflows/rank-distribution-weekly.yml)内でLP取得と保存が両方成功した後、`MR_DISTRIBUTION_WEEKLY_ENABLED=true`ならMRを取得する。互換性のためファイル名やSecret・変数名の`weekly`は維持する。手動LPはMRを連動させず、手動MRも別途実行できる。保管先・停止・認証更新・結果確認の手順は[日次取得の運用](weekly-collection.md)を参照。

7日後の判定には実時間の経過が必要で、日付を人工的に進めたテストや今日の手動実行だけで「1週間後にも使えた」とは扱わない。

## 次に進める作業

1. 変更後の日次runでLPからMRまでの取得・保存結果を確認する。起動設定と毎回の取得成功は分けて扱う。
2. 保存後、ページの取得日・総数が新しい集計と一致するか確認する。同梱データも新しくしたい場合だけ手動importを使う。
3. 認証の更新が必要になった場合は手動ログイン・再保存・共有Secretの削除と再送信を行う。定期取得だけを止める場合はLP workflowを無効化し、Legendも使う共有Secretを不用意に削除しない。

10月23日の[定期実行](https://github.com/gonchiman/sf6/actions/runs/39828328376)では自動起動と7日後の認証再利用を確認したが、分布全体の取得は未完了だった。10月28日の単発実行ではLP・MRとも取得・保存できた。一覧の生成日時を最新取得日として扱わず、それぞれの取得終了日時を確認する。
