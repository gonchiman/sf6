# 標本調査

`#sample-survey` は結果閲覧専用。公開済みの集計JSONを読み込み、ランク別のLP系列とMR帯別の系列を分けて表示する。取得設定と実行管理はGitHub Actionsに置く。

## 操作と対応範囲

1. 「取得日」で公開済みの観測回を選ぶ。最初は最新の結果を表示する。
2. 「LPランク」「MR帯」と7つの集計テーマを切り替える。初期テーマは実データのある「LP・MR」。活動・使用状況、キャラ別成績、相手キャラ別、戦闘傾向、直近の戦歴、属性・補助情報も表示対象とする。
3. 各テーマで公開された期間・モード、ランク・MR帯、使用キャラ、指標を選ぶ。表と横棒グラフは同じ条件で表示し、0を基準に比較する。割合の軸は0〜100％。取得状態、予定数・抽出数・有効標本数、欠測・重複、境界確認は「取得状況・集計条件」にまとめる。
4. 結果がない場合は「未取得」、通信・形式の問題は「読み込み失敗」、MRを取得しなかった回は「調査対象なし」と表示する。追加集計は未取得・取得失敗・分母0の算出不可・確認済み0件を区別する。

ローカル開発版とGitHub Pagesで同じ閲覧機能を使う。画面に計画保存・取得開始・停止・認証・JSON入出力の操作は置かず、ローカル取得APIも呼び出さない。既存の `StatisticsPanel`、取得期間表示、テーブル罫線を再利用し、テーマ切替と横棒グラフを追加した。

**追加プロフィール項目の取得器は未実装。** 今回は集計JSONの読み込み・検証・表示まで。現行Actionsが取得するのは従来のLP/MR標本であり、追加項目は集計が配信されるまで「未取得」となる。同じIDの次回再観測、信頼区間・人口全体の推定は未対応。デモ数値や個別プロフィールは配信しない。

### 追加集計の形式と意味

既存runのschemaVersion 1/2を保ち、optional `insights: { schemaVersion: 1, datasets: [...] }` を追加。型は [sampleSurveyInsights.ts](../../src/types/sampleSurveyInsights.ts)、検証は [sampleSurveyInsights.ts](../../src/lib/sampleSurveyInsights.ts)、表示名は [sampleSurveyPresentation.ts](../../src/lib/sampleSurveyPresentation.ts)。旧JSONもそのまま表示する。

各datasetはテーマ・LP/MR系列・期間・モード・取得開始終了・層別coverage・集計行を持つ。Actは具体的番号を必須とし、累計・取得時点・過去100戦・直近最大10件と区別する。既存MR標本の「取得時の今Act」に新しいAct番号を後付けしない。各層はrunに存在し、coverageの試行数はその層の標本数以内、正常＋失敗＝試行数とする。

| テーマ | 表示する主な値 | 集計条件 |
| --- | --- | --- |
| 活動・使用状況 | 期間内対戦あり割合、平均対戦数、平均使用キャラ数 | 期間・モード別、0戦・0キャラを含む有効標本 |
| LP・MR | 標本内平均・最小・最大 | 取得時の最大LP／今Act最大MR一覧 |
| キャラ別成績 | 使用者割合、勝数・対戦数、勝率、キャラ別LP/MR中央値 | 使用者は指定期間に1戦以上。勝率は合計勝数÷合計対戦数。LP/MRは取得時点の別dataset |
| 相手キャラ別 | 対戦数、アカウント別勝率中央値 | 自分・相手キャラ別。中央値は1戦以上の掲載勝率。全試合の勝率に置き換えない |
| 戦闘傾向 | ドライブ・SA割合、パリィ・インパクト・投げ・壁際等 | 各アカウントの公式「過去100戦」集計値の単純平均。全試合の合算値にしない |
| 直近の戦歴 | 最大10件/人の記録数、C/M/不明、勝敗、7日以内の記録あり | アカウント側の記録数で同一試合の重複あり。M割合はM÷(C+M)。ログイン時刻の代用にしない |
| 属性・補助情報 | 設定地域、プラットフォーム、ポイント、クラブ等 | 取得時点。地域は設定値、ランクマッチ時間は掲載者のみ |

各セルの `n` はその指標に寄与したアカウント数。件数・割合の分子分母・平均の合計値・中央値を明示的な型で保存する。割合は合算した分子分母から表示し、平均はセル固有のnで計算する。分母0は0％としない。テーマや対象外の項目・未知フィールド・不整合な分子分母・個別ID/名前/URLを拒否する。追加テーマの再観測やLP/MR系列を足し合わせて人口推定しない。

既存の公開JSON 256KiB上限を維持する。全ランク×全キャラ相性×多数Actなど、上限を超える集計にはテーマ別ファイル等への分割配信が別途必要。現行UIに合わせるために上限を緩和しない。

## GitHub Actionsでの取得

ワークフローは [sample-survey.yml](../../.github/workflows/sample-survey.yml)。mainへ反映後、Actionsの「Collect sample survey」から手動実行する。**この変更は手動実行の入口までで、定期実行のscheduleは設定していない。**

- 対象LPランク：カンマ区切り。初期値MASTER。MRのみなら空欄。
- 各ランク／MR帯の標本数：10〜1,000、10刻み。初期値10。
- MR帯の追加：初期は無効。有効時は6帯を対象とする。
- 取得時間上限：1〜120分、初期10分。準備・境界確認も含む。
- 保存認証：既存のリポジトリSecret `BUCKLER_WEEKLY_SESSION` を取得stepだけで利用する。保存済みであることは有効性の保証ではない。

GitHub hosted Windowsで画面ありのEdge、直列10秒の開始間隔を使う。既存ランク分布・並列取得テストと実行ロックを共有する。認証要求、人間確認、アクセス拒否、ページ形式や並び順の破損では停止し、自動再試行しない。

取得中の最初の読み取り失敗では、既存の診断機構が得た情報を `sampleSurveyFailureDiagnostic` の1行JSONとしてActionsログへ出力する。HTTP状態、認証表示、一覧の読み取り可否、通信失敗の分類、直近の最大32イベントを許可フィールドだけで再構成し、64KiB以内に制限する。URL・Cookie・個別ID・DOM・例外本文は出さない。診断の不正やログ出力失敗は元の停止理由を変更しない。診断は公開集計・履歴には含めず、認証条件・確認期限・取得間隔も変更しない。

新しいschemaVersion 2では、取得手順を完了した結果を、層ごとの「前後一致」「要確認」と欠測・重複を残したまま公開する。全層の境界が未確定で標本もない回、不完了・失敗の回は公開せず、以前の結果を保持する。境界を確認できた人口0の層は、未取得と区別して0件として扱う。旧schemaVersion 1の公開基準は、従来の範囲変更・欠測・重複なしを維持する。

公開するのは集計JSONのみで、個別ID・名簿・CookieをArtifactや履歴へ含めない。取得ジョブはread権限、公開ジョブだけcontents writeを持ち、公開ジョブにはBuckler認証を渡さない。Actions成功は取得手順と公開の完了を意味し、全層の境界が一致したことを意味しない。

クラウドでは抽出位置・個別観測・進捗をメモリ内だけに保持する。各実行で新しく抽出するため、中断した回の再開や同じ標本の継続観測は行わない。

### 結果の公開と読み込み

履歴ブランチ `codex/sample-survey-history` の `public/data/sample-survey/index.json` と `runs/<runId>.json` を使う。manifestには最新100回までを掲載し、同じ実行IDの内容は変更しない。取得・公開の両段階で公開スキーマ、最大256KiB、許可ファイルだけであることを検証する。

画面は履歴ブランチを優先し、取得できない場合はアプリ同梱のmanifestへ切り替える。同梱結果を使う場合はその状態を表示する。初期の同梱manifestは空で、架空の観測結果は含めない。選択された回のJSONだけを読み込み、取得日変更後に前の回の値を混在させない。

ランキング変動対応後の再テスト（同日20:22:43〜20:30:58 JST、[run 40495597706](https://github.com/gonchiman/sf6/actions/runs/40495597706)、コード `a1a1c941`）は同じMASTER10件・MRなし・直列10秒・上限10分で成功した。約8分15秒、50試行中50ページ読取成功、有効標本10件、欠測0・重複0。MASTER境界は551,604から551,605へ動き、層の前後掲載総数は3,097,303から3,097,311へ増加した。`review-required`（要確認）として処理を完了し、集計Artifact1件と履歴ブランチへの保存に成功した。取得ログと公開JSONの一致をスキーマ検証込みで確認した。

この結果は標本内の参考集計であり、MASTER全体を代表する精度の検証ではない。取得開始前の境界探索を含む最初の掲載総数は3,097,302で、変化履歴に残る。層の前確認値3,097,303とは観測時刻が異なる。

境界探索短縮後のActions実測（2026年10月28日13:15:52〜13:21:27 JST、[run 40631277446](https://github.com/gonchiman/sf6/actions/runs/40631277446)、コード `bfc3d5c1`）も、MASTER10件・MRなし・直列10秒・上限10分で成功した。34試行中34ページ読取成功、有効標本10件、欠測0・重複0、所要334.045秒。前回の50ページ・494.504秒に対し、読取16回（32％）・160.459秒を削減した。MASTER境界は前後とも551,848で一致し、層の前後掲載総数は3,098,574から3,098,576へ増えた。`checked`（前後一致）として集計Artifactと履歴へ保存し、公開JSONと取得ログの一致も確認した。別時刻・別標本での1回ずつの実測比較であり、常に同じ短縮率になることを保証しない。

全8ランク各10件の初回Actions試験（2026年10月29日11:54:56〜12:39:00 JST、[run 40809085933](https://github.com/gonchiman/sf6/actions/runs/40809085933)、コード `b4bfa214`）は44分03.382秒で停止した。264試行中263ページを読み取り、ROOKIEとBRONZEを各10件取得したが、IRON・SILVER・GOLD・PLATINUMは抽出前の開始境界確認で不一致となり未取得。DIAMONDの境界探索中に `authentication-unconfirmed` で停止し、MASTERは未開始だった。Artifact・履歴更新はなく、旧結果を保持した。

## 抽出と停止後の扱い

LPはROOKIE〜MASTERの8ランクから選ぶ。MR区分は1200未満、1200〜1399、1400〜1599、1600〜1799、1800〜1999、2000以上。両系列のアカウント重複は全体の観測件数から除外し、各系列の統計は別に保持する。MR系列をLP系列の人口推定へ足し合わせない。

固定条件の最大LP一覧と観測時の今Act・最大MR一覧で、ランク／MR帯ごとに「境界の二分探索と新しい隣接行による確認 → 抽出位置を固定 → その層を取得 → 境界を再確認」を行う。全層の探索が終わるまで標本取得を待たず、層ごとの観測期間を短くする。各区間内の掲載位置をseed付きで重複なしに抽出し、同じページの位置をまとめる。層内の取得ページ順を混ぜ、選ばれた位置だけを台帳に記録する。

取得後の境界探索では、取得前に確認した開始・終了位置の近くから探す。新しく読んだページから境界を挟む位置を探し、見つからなければページ単位で探索幅を倍々に広げる。近傍探索は各境界6回までとし、それで候補が定まらなければ最新の総数を使う全範囲の二分探索へ戻す。候補が見つかっても、従来どおり新しく読んだ境界の隣接行で確認する。過去の位置を探索の手掛かりに使うだけで、過去のページを現在の根拠として使わない。

途中再開でも、その層の保存済み境界を探索の手掛かりにする。対象LP／MR、層、ページサイズが一致する場合だけ使用し、範囲が変わっていれば従来どおり再開を停止する。新規実行の初回探索は全範囲から始める。別のActions実行やランク分布の履歴から境界を取り込む機能は含めない。直列10秒の開始間隔・取得時間上限・固定した抽出位置は維持する。

ランキング全体の総数が変わっただけでは即停止しない。各層の開始・終了総数、取得前後の境界、確認時刻を保存する。対象境界が変わった層は「要確認」とし、他の層と区別する。

新規層の抽出前に境界候補を得られたものの、新しい隣接行の確認が一致しなかった場合は、その候補位置を使って最大2回追加で近傍探索・確認を行う。最終的に確認できた範囲を取得前の境界とし、その後で初めて標本位置を固定する。補正前の不一致・境界変化の記録は保持し、補正した層は「要確認」とする。候補が成立しない場合や、追加確認の上限でも一致しない場合は「未取得・要確認」として次の層へ進む。認証・HTTP・形式の失敗や取得上限はこの補正の対象にせず停止する。

この最大2回の補正では、開始境界の近傍探索直後に新しいページで確認し、その後に終了境界の近傍探索と確認を続ける。終了側の探索と先頭ページ再読を開始境界の確認前に挟まない。探索と確認、開始側と終了側のページキャッシュは分離する。終了側の探索が2回以上のページ取得または全範囲の探索を要した場合は、従来の両端確認を行い、先に確認した開始境界をそのまま受理しない。末尾の総件数に依存する境界と空の母集団は、新しくページを読んだ状態で確認する。初回探索・途中再開・取得後の確認は従来の手順を維持する。

この順序変更は候補を読んでからその候補を確認するまでの時間を短くするもので、開始と終了の境界を同時刻に固定するものではない。開始境界の確認後も終了側の探索と確認が残るため、標本を選ぶまでに変動する可能性は残る。補正した層の「要確認」、取得時の層外・重複判定、取得後の境界確認は保持する。

保存済みの標本位置がある途中再開と、抽出後の確認では、境界補正による位置変更や再抽出をしない。対象外へ移った枠や同一系列内の重複は欠測・重複として残し、別の取りやすい人で補充しない。

総数・境界の開始位置／終了位置・ページサイズ・並び順・区間逆転・層外・重複・ページ不在を別の種別で記録する。公開記録は時刻と変更前後の数値のみで、最大64件。古い記録を省いた数も保存し、個別IDやURL、生の例外は含めない。

前後の境界一致は、途中に順位移動がなかった証明ではない。結果は観測期間中に取得した標本内の統計として表示する。固定母集団からの厳密な無作為抽出や、その時点の全体推定・誤差保証は提供しない。

検証用のローカル取得サービスには中断・再開機能が残るが、結果ページからは操作しない。新形式のLP再開時は途中の層の境界を確認し直し、保存済みの抽出位置・取得済み観測を保持する。確認済みの層は再取得せず、未開始の層を順番に追加する。途中層の範囲が変われば停止する。旧checkpointは読み取りを維持するが、新方式へ混ぜて再開しない。境界確認より短い時間上限では、再開しても準備を終えられない場合がある。

**具体的なAct番号の取得・照合は未対応。** MRの値を一度でも観測した回は、別Actの値が混ざらないよう中断後の再開を無効にする。LPのみの調査、またはMR観測前の回は上記条件で再開できる。MR結果の対象期間は各行の観測時点の「今Act」であり、一つの確定したAct番号を保証しない。

開始間隔は全体で10秒、直列。読み取り回数は `floor(時間上限 / 10秒) + 1` 以下で、境界確認・再読も含む。標本数だけでは完了時間を保証できない。結果ページには取得時間の見積もりを表示しない。

## 検証用ローカルサービスの保存

- 非公開台帳：`.local/sample-survey/observations.sqlite`。計画、境界、抽出位置、選ばれたCFN ID・LP/MR・ランク・観測時刻、進捗を保存する。
- 読取失敗の診断：`.local/sample-survey/diagnostic-<runId>.json`。同じ実行の内部エラー分類、HTTP番号、通信・DOM評価の到達段階を保存する。同じ実行IDでは最初の診断だけを残し、再開後も上書きしない。イベントは最大32件、ファイルは64KiB以下に制限し、URL・Cookie・CFN ID・個別行・生の例外文字列は含めない。診断保存が失敗しても元の停止理由を保持する。
- 集計JSON：公開スキーマで検証した統計と件数のみ。CFN ID、対象者名簿、個別行、認証情報は含めない。
- SQLiteのトランザクション、プロセス所有権、保存済み観測の不変性を確認する。別の開発サーバーが同じDBを所有している間は開始できない。
- `.local/` はGit対象外で、Viteからの直接配信も拒否する。SQLite自体を暗号化しているわけではない。既存の暗号化認証ファイルは別管理とする。

ローカルAPIは `/sf6/__sample-survey/`。ループバック接続・Host・Originを検証し、変更操作には起動時tokenを要求する。応答は計画と集計のみで、私的な例外文字列は返さない。通信が切れたPOSTを自動再送せず、状況を再確認する。保存障害時も取得停止は受け付ける。
