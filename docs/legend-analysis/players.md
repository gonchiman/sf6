# レジェンド帯分析2：プレイヤー一覧

`#legend-analysis-2` は、共通ヘッダーに取得日の選択だけを置き、その直下に「プレイヤー一覧／グラフ」のタブを表示する。初期表示はプレイヤー一覧とする。一覧は「順位・プレイヤー・ID・キャラ・MR・国／地域・プラットフォーム・対戦数」の8列。対戦数は掲載キャラの今Actのランクマッチ数。1行はアカウント×掲載キャラで、同じ名前や同順位も別行として保持する。初期順は順位昇順。各列を昇降順で並べ替えられる。キャラは既存の日本語台帳を利用する。

タブ切り替えでは両パネルを保持し、一覧の並び順・スクロール位置、グラフの種類、選択プレイヤーを維持する。取得日を変えても表示タブは維持する。タブは既存の勝率・使用率相関ページから共通化した `ContentTabs` を使い、左右キー・Home・End操作とARIAの関連付けを揃える。

出典、集計単位、同梱データ利用時の表示、Act、地域・プラットフォーム、順位・MRの取得区間と対戦数の取得区間（JST）、最新取得の失敗・検証待ちや更新確認失敗は、両タブに共通する本体下部の取得情報へまとめる。最新取得状況と確認日時は、選択データの取得区間とは別に表示し、更新の再確認ボタンを維持する。掲載件数と一覧の対戦数対象期間は各パネルの見出しに残す。キャラ名の読込失敗はタブ直下、一覧の読込失敗は一覧内に表示する。取得記録が1回分でも取得日の選択欄を表示し、記録が増えると切り替えられる。取得記録がない場合は選択欄を表示しない。未取得・検証待ち・取得失敗・読込失敗・検証済み0件は区別する。既存 `#legend-analysis` の集計とグラフは変更しない。

## 一覧の絞り込み

一覧の上にプレイヤー名の検索欄とキャラの単一選択を置く。名前はNFKC・前後空白除去・日本語ロケールの小文字化を照合時だけ行い、部分一致で絞り込む。元の表示名や行IDは変更しない。名前とキャラの条件はANDで適用し、結果に既存の並び順を適用する。キャラの候補は絞り込み前の掲載キャラと現在選択中のキャラから作り、日本語台帳の名称を使う。台帳にないIDはID表示とする。

「表示件数 / 全掲載件数」を表示し、取得済みの行が条件に合わない場合は「該当するプレイヤーがいません」とする。未取得・読込失敗や確認済み0件とは区別する。名前を空にし、キャラを「すべて」にすると全行に戻る。

条件と並び順は日付・タブ変更でも保持する。別の日に選択キャラの掲載がなくても、その条件を保って該当なしとする。条件を変更したときだけ一覧内の縦スクロールを先頭へ戻す。入力欄・選択欄は既存のキャラ情報ページと `win-rates-filters` の表示を踏襲し、表は `LegendPlayersTable` と `table.css` を再利用する。

絞り込みは一覧のみに適用し、グラフは全掲載行を表示する。グラフの選択行が条件外の場合も条件を自動解除せず、一覧にその行を追加しない。選択IDは保持し、表示中の対象行がある場合だけ選択行へのスクロールを行う。追加取得は行わず、読み込んだ一覧JSONをブラウザー内で絞り込む。

## グラフ

選択中の一覧JSONだけからブラウザー内で計算し、追加のBuckler取得は行わない。「順位とMR」「キャラ別掲載数」「MR帯の分布」のボタンで切り替え、初期表示は「順位とMR」。グラフと表の取得日は共通で、読込中・失敗時に別の日のグラフを残さない。

- **順位とMR**：横軸は公式掲載順位、縦軸はMR。通常は順位順の線だけを単色で表示し、選択行の位置だけ点とガイドで強調する。1件のみ、または全行が同じ座標で線を描けない場合は、小さな点を1つ表示する。MR軸は観測範囲に合わせ、目盛りを明示する。同順位・同MRの複数行を維持する。線の近くのクリックとキーボードで行を選択でき、プレイヤー名・キャラ・順位・MRを表示する。
- **キャラ別掲載数**：取得行をキャラIDで数え、件数の多い順に全掲載キャラを1つの縦棒グラフで表示する。横軸はキャラ、縦軸は掲載件数（0件起点・整数目盛り）。件数は棒の上、キャラ名は棒の下に60度傾けて表示する。文字幅に応じて余白と最小列幅を確保し、狭い画面ではグラフ内だけを横スクロールする。段分けや上位件数による省略はしない。キャラ名が台帳にない場合はIDを表示する。ユニーク人数や対戦での使用率とは扱わない。全キャラ台帳に存在するだけのキャラを、掲載0件として補完しない。件数軸・集計は既存の共通処理、文字幅は `chartTextWidth` を使い、配置は `ExpectedMatchesChart` と `BalanceAdjustmentCountChart` に揃える。
- **MR帯の分布**：既存の `summarizeLegendMr` を使い、50 MR刻み・下限以上／上限未満で集計する。横軸はMR、縦軸は掲載件数（0件起点）。最小値から最大値の間の0件階級も省略しない。構成比の分母は選択取得回の全掲載行数。

順位グラフの選択とテーブルの行強調は取得ID＋行IDで連動する。表の行選択時はグラフの種類を「順位とMR」に設定し、一覧タブに留まる。グラフから選ぶと、次に一覧タブを開いたとき表内だけをスクロールして選択行を見せ、ページ全体は動かさない。同じ選択のまま再びタブを往復した場合は、手動で動かしたスクロール位置を保つ。並べ替えても同じ行の選択を保持し、別取得回へ切り替えたときは解除する。同じ取得回の公開情報更新では選択を保つ。取得回内IDや名前を、取得日を跨ぐ個人の同一性判定に使わない。

検証済み0件ではグラフを描かず「0件（取得確認済み）」とする。未取得や読込失敗を0件に置き換えない。プレイヤーごとの時系列や勝率のグラフは表示しない。

## データと保存

- 既存の集計JSONからプレイヤー一覧は復元できない。過去の一覧JSON（schemaVersion 1）は保持し、追加4項目を「未取得」と表示する。過去データに推定値や0を補わない。
- `--players` を明示した取得は、ランキングに表示された名前・公開プレイヤーID・国／地域・プラットフォームを読み、掲載アカウントの公開PLAYページから掲載キャラの今Actランクマッチ数も取得する。同一プレイヤーIDのプロフィールは取得回内で1回だけ読み、複数の掲載キャラへ対応する値を使う。
- 名前は2026-10-28に実画面で確認した、ランキング行内の `span[class*="ranking_name__"]` を読む。称号やコメントを名前に混ぜず、国／地域とプラットフォームも取得元の表示ラベルを保持する。
- 新しい一覧JSON（schemaVersion 2）は `players: [{ id, playerName, playerId, characterId, rank, masterRating, region, platform, rankedMatchCount }]` と出典・取得区間・Act・条件・検証情報を持つ。`id` は取得回内の連番、`playerId` は公開IDの数字文字列で、先頭ゼロも保持する。名前で同一人物を判定しない。
- `rankedMatchScope` に `actId`・`mode: "ranked"`・`collectionStartedAt`・`collectionEndedAt` を保存する。プロフィール取得区間を順位・MRの取得区間と分け、同じAct・掲載キャラ・ランクマッチであることを確認する。manifestはschemaVersion 1を維持し、集計と一覧の共通descriptorは順位・MRの取得区間で一致させる。
- 全掲載行の必須項目と対戦数を確認した場合はschemaVersion 2で保存する。ランキング全件の検証完了後にプロフィール取得が失敗した場合は、全掲載行の名前・ID・キャラ・順位・MR・国／地域・プラットフォームをschemaVersion 3で保存する。途中まで読めた対戦数も全て除外し、過去値で補わず、確認済み0回と未取得を区別する。
- schemaVersion 3は `rankedMatchAvailability: { status: "unavailable", reason, checkedAt }` が必須で、`rankedMatchScope` と全行の `rankedMatchCount` を禁止する。理由は認証未確認・取得元未確認・取得元変化・アクセス不可・期限切れ・上限・取得失敗の固定分類。確認日時はランキング取得終了から生成日時までの範囲とする。表の対戦数は「未取得」、取得情報は「取得失敗」と確認日時を表示する。旧schemaVersion 1/2の契約は変更しない。
- プロフィールURL・一時照合ハッシュ・認証情報は保存しない。表示名やラベルは文字列として扱い、HTMLとして実行しない。
- 公式Legend表示・末尾・先頭・重複・MR順・Actなどの既存検証、5秒の取得開始間隔、アクセス拒否やCAPTCHAでの停止条件を再利用する。ランキングの全件取得失敗を部分一覧や0件で代替しない。対戦数の成否だけをランキングの成否から分離する。
- 通常の `data:collect-legend-analysis` は集計専用。日次workflowの一覧出力は明示的な設定で有効化し、最初は手動単発で確認する。

## Actionsでの単発確認と日次運用

既存の `Collect daily Legend analysis` を利用する。実行はmainのコード・GitHub hosted Windows・既存の保存認証に限定する。一覧を有効化すると、ランキングの確認後に掲載アカウントのプロフィールを巡回する。

取得開始間隔は5秒以上。一覧取得時の内部期限は120分、readerが開始するページ遷移とモード変更は合計2000回まで、異なるプロフィールは1000件まで。画像等を含む実HTTP通信全体の件数ではない。公式Legend表示を基準にするため500件で切らず、同率掲載も含める。上限を超えた場合は部分一覧を公開しない。Actionsの取得jobは一覧有効時130分、集計専用時20分で打ち切る。

1. mainへ反映後、手動実行の `include_players` を `true` にして単発取得する。初期値は `false`。この手動入力はその1回だけに適用される。
2. 取得・検証・Artifact・履歴保存とページ表示の成功を確認する。
3. 成功後にリポジトリ変数 `LEGEND_PLAYERS_DAILY_ENABLED` を文字列 `true` に設定すると、以後のscheduleで一覧も保存する。未設定または `true` 以外なら日次は集計専用のまま。

取得jobと履歴保存jobには、同一の厳密な真偽値を渡す。一覧を有効化したのにファイルがない、無効なのに一覧が含まれる、集計と一覧の取得回が一致しない場合はアップロードや保存を止める。

Artifactは検証した集計JSONと `public/players/index.json`・`public/players/legend-*.json` だけ。認証を受け取らない保存jobで両方を再検証し、既存の `codex/legend-analysis-history` ブランチへまとめて保存する。各データ種別は既存の厳密なvalidatorと不変履歴publisherを使い、両方を組み立ててから履歴ディレクトリを入れ替える。一覧を無効化した日の集計更新でも過去の一覧を保ち、取得失敗では失敗状況と以前の正常な一覧を保持する。

ランキング完了後のプロフィール取得だけが失敗した場合、取得レポートは `status: "partial"` と失敗理由・保存した取得IDを持つ。Actionsの取得jobは未完了項目の通知のため失敗扱いを維持し、保存jobは検証済みの集計とschemaVersion 3の全一覧を保存する。両manifestへ同一の取得descriptorと「ランキング一覧は取得済み、対戦数は未完了」の状態を設定するため、失敗したjobでも新しいランキングが保存される場合がある。個別プロフィール取得は最初の未回復エラーで停止し、追加の再試行を始めない。

この保存はランキングの検証が完了した後だけに限る。プロフィール中のAct変更では元の取得区間・元のActのランキングを保持し、対戦数は保存しない。内部の取得期限で止まった場合も同様。明示的な利用者キャンセル、ランキング未完了、時計異常、ブラウザー終了失敗では新しいランキングを保存しない。出力失敗はArtifactを許可しない。

診断ログの `attemptFailures` に、全体の取り直し前と最終失敗の試行番号・段階・ページ番号・エラー分類・検証項目・再確認差分の分類を保存する。`humanVerification` はWAFヘッダーの確認有無・分類と可視DOMの人間認証検出結果を持ち、未観測と非検出を区別する。本文・認証値・個別プレイヤーの名前やIDは診断ログに入れない。CAPTCHAやアクセス拒否の停止条件は維持する。

取得の最後に行う先頭・末尾の再確認では、ページの表示範囲・条件・Actと、全行のアカウント×キャラの集合・各項目のLegend判定・取得対象の場合の公開プレイヤーIDが一致することを要求する。再読ページ自体の順位・MR順、重複、行位置とLegend表示の連続性も検証する。同じ掲載メンバー内の順位・MR・表示名などの更新やページ内の並び替えだけであれば、全体を取り直さない。掲載メンバー・キャラ・Legend判定・表示範囲の変更は引き続き拒否する。

受理した場合も、全体の重複・順序を検証済みの元の観測値を一覧・集計に使い、再確認ページの最新値だけを部分的に上書きしない。取得区間内の断面であり、全ページの同時点性や取得終了時の最新値を保証しない。範囲復帰後に行う左隣の再確認には、下記のページ境界の検査も適用する。

`endpointRechecks` に、比較した試行・先頭／末尾・ページと、`unchanged`（完全一致）／`same-members-updated`（同じ掲載項目で値や並びが変化）／`rejected`（採用不可）を残す。差分は `rank`・`master-rating`・`player-labels`・`row-order`・`membership`・`legend-status`・`metadata`・`invalid-page` の固定分類だけを保存し、名前や照合値を含めない。各全体試行で先頭と末尾の最大2記録、全体で最大6記録とする。通信・認証などでページを読み取れなかった場合には記録を補わず、返されたページの条件・値が不正なら `invalid-page` を残す。診断はログだけに出力し、公開JSONに含めない。

順位順・MR順の検証失敗では、`attemptFailures[].orderDiagnostic` にページ内／ページ間の区分と、比較した前後のページ番号・1始まりの行位置・順位・MRを残す。前後が同じ掲載項目か、現在の項目が採用済みページや現在ページ内に重複するかは真偽値だけを残し、照合に使うID・名前・キャラID・ハッシュは出力しない。

この失敗時だけ、1秒待って表示中のランキングDOMを1回だけ再観測し、`orderRecheck` に記録する。この観測自体は新しいページ遷移・リクエストを開始せず、正常でも失敗したページの採用には使わない。下記の範囲再確認へ進む場合は、画面が別ページになる前にこの診断を採取する。再確認が失敗した場合も元の逆転の診断と実際に失敗した検証項目を残す。CAPTCHA・アクセス拒否・認証要求・キャンセルは再観測でも直ちに停止する。再観測できなかった場合も元の診断を残し、未観測を数値0や一致に置き換えない。

`orderRecheck` は固定の状態分類、経過ミリ秒、ページ・表示範囲・総掲載件数、前後の順位・MR、ページ内の順位・MR逆転の有無を持つ。`sameEntries`・`sameRanksAndMr`・`currentSameEntry`・`previousSameEntry` は元の観測との一致を表す真偽値だけで、照合値そのものは含めない。ページ間の比較では直前の行が別ページにあり、現在ページのDOMだけでは再観測できないため、`previous` と `previousSameEntry` は `null` になる。

範囲再確認の適格性を判定した失敗では、`attemptFailures[].pageRecoveryDecision` にきっかけ（順位順・MR順・重複）、対象ページ・直前ページ、以前に再確認を開始したかどうか（`recoveryUsed`）、適格性と最初に拒否した理由を残す。以前の再確認があること自体は拒否理由にしない。`reason` は次の固定値とし、実際の判定順に記録する。

| reason | 意味 |
| --- | --- |
| `eligible` | 範囲再確認の対象 |
| `within-page-order` | 最初の逆転がページ内で発生 |
| `recovery-already-used` | 過去の1回制限で、再確認枠の使用済みにより対象外となった記録 |
| `previous-page-missing` | 採用済みの直前ページがない |
| `nonadjacent-page` | 採用済みページと現在ページが連続していない |
| `within-page-rank-order` / `within-page-mr-order` | 現在ページの後続行にも順位・MRの逆転がある |
| `within-page-duplicate` | 現在ページ内で同じ掲載項目が重複 |
| `recovery-range-too-wide` | 必要な範囲が6ページを超える |
| `earlier-page-duplicate` | 過去の2ページ再確認で、直前より前の採用済み項目との重複により対象外となった記録 |

内部の逆転・重複で対象外となった場合は、`conflict.previous` と `conflict.current` に比較元と該当行のページ番号・1始まりの行位置・順位・MRを保存する。先頭行の逆転とは別に、後続行で対象外になった位置も確認できる。最初の理由だけを記録するため、他の異常がないことを意味しない。重複照合に使ったID・名前・キャラID・ハッシュは保存しない。判定は取得済みの行だけで行い、この記録のための追加通信や待機はしない。

`eligible: true` は適格性判定を通ったことだけを表し、再観測中の停止などで実際の再確認が始まらないこともある。開始・成功は既存の `pageRecoveryAttemptCount`・`pageRecoverySuccessCount` と分けて確認する。再確認中の失敗や全体の取り直し後も、その試行の判断を残す。再確認に成功した判断は後続の無関係な失敗に混ぜず、対象の判定を行っていない失敗や旧形式の記録には値を補わない。

取得レポート直下の `pageRecoveryRanges` は、開始順に各再確認の試行番号・開始ページ・終了ページ・検証が済んだ最後のページと、`started` / `succeeded` / `failed` を保持する。1回の再確認につき1記録を進捗に合わせて更新し、全体の取り直しでも過去の記録を消さない。既存の `pageRecoveryRange` は最後の再確認を表す。範囲を読み直しただけでは成功にせず、既知メンバーと左隣ページの確認を含めて通過した場合だけ `succeeded` とする。範囲の復帰成功後に別の検証で停止しても、この記録を保持する。範囲復帰の成功と取得全体の成功は区別する。未開始や旧形式のレポートには履歴を補わない。

再確認中に重複・欠落を検出した場合は、その範囲記録の `issues` に分類と当時の範囲を残す。重複は「固定した前方ページとの重なり」「再読範囲内のページ間重複」「同じページ内の重複」に分け、比較した前後のページ・行位置・順位・MRだけを記録する。欠落は件数と以前の数値位置を最大3件記録する。範囲を拡張する場合は変更後の開始・終了ページも残す。範囲が広がる回数には上限があるため `issues` は最大5件とし、旧形式に値を補わない。名前・ID・照合ハッシュは含めない。

識別キーは取得回で固定したsaltとプロフィールのパス・キャラIDから作られ、順位・MR・名前の変化だけで変わる不具合は見つからなかった。ただし、古い読み込み済み画像と有効な画像指定が異なる合成DOMでは、同じアカウントを別キャラとして識別する検証の抜けを再現したため、画像の整合性確認も追加した。これは入力が矛盾する場合の防御であり、以前の1件が実際にこの矛盾によって発生した証拠ではない。以前のログは識別情報とアカウント単位の照合差分を保存していないため、その1件の移動先や掲載変更を後から特定できない。今後は数値と分類だけの `missingDetails`・`edgeProbes` と画像矛盾のエラー分類で切り分ける。

この追加修正は関連テスト272件・ビルドで検証した。16ページ2行目・298位・1814 MRで観測した項目が19ページへ移る合成ケースでは、左隣の不変と右隣の所在を確認して6ページへ拡張し、全体を完了した。左隣の既知項目を捨てないこと、9読取分がない場合は隣接確認を始めないこと、新しく読んだ右隣の項目も欠落させないこと、非Legendとして再発見した場合とCAPTCHAでは停止することを確認した。画像については有効な指定の矛盾・解消・正常なサイズ違い・古い非表示fallbackを区別する。直前の実取得がCAPTCHAで終わったため、この修正作業では新たなBuckler取得を行っていない。

2026-11-05の[単発検証](https://github.com/gonchiman/sf6/actions/runs/42000117828)は `aee168f` で18:10:28〜18:14:19 JSTに実行した。最初の試行は終端までの巡回と末尾再確認を通過したが、最後の先頭ページ再確認で `legend-entries` の差分を検出した。2回目の13ページ目でHTTP 405と `wafAction: "captcha"`・`domDetected: true` を確認して停止した。読取45回・成功42回、範囲再確認0回、プロフィール0件。履歴保存は成功し、正常な集計14回・一覧5回を維持した。具体的な差分は既存の分類から判別できず、この実行では欠落調査の追加分岐も動いていない。

この記録を受け、上記の最終再確認を掲載集合と値の変化に分ける。MRや名前だけの更新でも必ず全体を取り直す実装上の問題は合成データで再現できるが、前回の差分が値の更新だけだったとは断定しない。既存の検証・一括公開・履歴保持を再利用し、兄弟プロジェクトの固定リビジョン取得はBucklerに確認済みの固定版がないため移植しない。

この修正は関連テスト284件・ビルド・共通ルール検証で確認した。同じ掲載項目の値更新・同率並べ替えで元の観測値を保存すること、項目の出入り・ID・Legend判定・範囲変更と不正な順位／MR順・重複では公開しないこと、CAPTCHA・通信予算の停止が変わらないこと、追加診断に個別情報が混入しないことを検証した。

修正を `4a5e3f1` でmainへ反映し、[一覧を含む単発検証](https://github.com/gonchiman/sf6/actions/runs/42005019976)を2026-11-05 18:46:09〜18:49:59 JSTに実行した。17〜18ページと20〜23ページの範囲再確認がともに成功し、末尾26ページは `unchanged`、先頭は `same-members-updated` / `master-rating` で受理した。ランキング全体が1回で検証完了し、全体の取り直しは0回だった。これは新しい値更新判定による実サイトでの成功記録である。

その後、対象468アカウントのうち1件のプロフィールを取得した後、2件目のモード選択時にHTTP 405と `wafAction: "captcha"` を確認して停止した（DOM検出はfalse）。読取45回・ランキング読取成功39回。この時点ではプロフィール失敗でランキングも破棄する旧保存処理だったため、新しいデータは公開されなかった。この結果を受けてschemaVersion 3への保存分離を追加した。CAPTCHA停止後は実サイトへの追加取得を行わず、取得済みランキングを模した合成データで保存・通知・履歴・画面を検証する。

保存分離後の関連テスト301件で、プロフィール中の認証・CAPTCHA・上限・Act変更・内部期限では全ランキングと未取得状態を保存できること、明示キャンセル・一時的な時計異常・終了失敗では保存しないことを確認した。日次Artifactと不変履歴への保存、旧v1/v2の互換、対戦数の0と未取得の表示も検証した。ランキング取得の成功は実サイト確認済みだが、schemaVersion 3の公開保存はこの時点では合成テストでの確認に限る。

## 操作

```powershell
# このチェックアウトに既存の保存認証がある場合の単発取得
npm run data:collect-legend-players
# 表示された取得回の public/players を指定
npm run data:import-legend-players -- .local/legend-analysis-daily/captures/<取得回>/public/players
npm run validate:legend-players
npm run test:legend-analysis
npm run build
```

取り込み先は `public/data/legend-players/`。既存集計の取り込みと同じ、検証・不変の取得ID・作業フォルダーからの入れ替えを再利用する。一覧の取り込みに失敗しても以前の正常データを保つ。公開リポジトリへのプッシュやデプロイは別の操作。

ページの読込は共通の `usePublishedData` と `createPublishedDataFeed` を再利用し、起動時・表示中5分ごと・タブへ戻ったときに確認する。一覧の配信元は既存履歴ブランチの `public/players/`。そこに完全な検証済みデータがない間は同梱JSONを使う。ページを開く操作はBuckler取得を開始しない。

## 再利用

SF6の `LegendCharacterTable` のソートとアクセシビリティ、`table.css`、`StatisticsPanel`、取得記録・配信読込・不変履歴の検証を利用する。兄弟プロジェクトの一覧を参照し、SF6の既存テーブルを拡張する。

グラフ切替はランク分布ページのボタン操作、件数軸は `legendPlayerCountAxis`、文字幅は `chartTextWidth`、MR集計は `summarizeLegendMr` を再利用する。キャラ別縦棒の名前・横スクロールは `ExpectedMatchesChart`、棒の上の件数表示は `BalanceAdjustmentCountChart` の配置を参照する。順位グラフは `WinUsageScatterChart` のサイズ測定・選択操作と、兄弟 `arknights_2` の `OperatorPcaScatter` の点選択を参照する。既存scatterの割合軸やキャラID一意という前提は適用せず、順位・MR・取得回内行IDに対応した部品として分離する。
