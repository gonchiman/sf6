# レジェンド帯分析2：プレイヤー一覧

`#legend-analysis-2` は、取得日の選択、グラフ、プレイヤー一覧の順に表示する。一覧は「順位・プレイヤー・ID・キャラ・MR・国／地域・プラットフォーム・対戦数」の8列。対戦数は掲載キャラの今Actのランクマッチ数。1行はアカウント×掲載キャラで、同じ名前や同順位も別行として保持する。初期順は順位昇順。各列を昇降順で並べ替えられる。キャラは既存の日本語台帳を利用する。

順位・MRの取得区間と対戦数の取得区間（JST）、Act、地域・プラットフォーム、出典、掲載件数を表示する。取得記録が1回分でも取得日の選択欄を表示し、記録が増えると切り替えられる。取得記録がない場合は選択欄を表示しない。未取得・検証待ち・取得失敗・読込失敗・検証済み0件は区別する。既存 `#legend-analysis` の集計とグラフは変更しない。

## グラフ

選択中の一覧JSONだけからブラウザー内で計算し、追加のBuckler取得は行わない。「順位とMR」「キャラ別掲載数」「MR帯の分布」のボタンで切り替え、初期表示は「順位とMR」。グラフと表の取得日は共通で、読込中・失敗時に別の日のグラフを残さない。

- **順位とMR**：横軸は公式掲載順位、縦軸はMR。通常は順位順の線だけを単色で表示し、選択行の位置だけ点とガイドで強調する。1件のみ、または全行が同じ座標で線を描けない場合は、小さな点を1つ表示する。MR軸は観測範囲に合わせ、目盛りを明示する。同順位・同MRの複数行を維持する。線の近くのクリックとキーボードで行を選択でき、プレイヤー名・キャラ・順位・MRを表示する。
- **キャラ別掲載数**：取得行をキャラIDで数え、件数の多い順に全掲載キャラを1つの縦棒グラフで表示する。横軸はキャラ、縦軸は掲載件数（0件起点・整数目盛り）。件数は棒の上、キャラ名は棒の下に60度傾けて表示する。文字幅に応じて余白と最小列幅を確保し、狭い画面ではグラフ内だけを横スクロールする。段分けや上位件数による省略はしない。キャラ名が台帳にない場合はIDを表示する。ユニーク人数や対戦での使用率とは扱わない。全キャラ台帳に存在するだけのキャラを、掲載0件として補完しない。件数軸・集計は既存の共通処理、文字幅は `chartTextWidth` を使い、配置は `ExpectedMatchesChart` と `BalanceAdjustmentCountChart` に揃える。
- **MR帯の分布**：既存の `summarizeLegendMr` を使い、50 MR刻み・下限以上／上限未満で集計する。横軸はMR、縦軸は掲載件数（0件起点）。最小値から最大値の間の0件階級も省略しない。構成比の分母は選択取得回の全掲載行数。

順位グラフの選択とテーブルの行強調は取得ID＋行IDで連動する。表の行選択時は「順位とMR」へ切り替える。グラフから選ぶと表内だけをスクロールして選択行を見せ、ページ全体は動かさない。並べ替えても同じ行の選択を保持し、別取得回へ切り替えたときは解除する。同じ取得回の公開情報更新では選択を保つ。取得回内IDや名前を、取得日を跨ぐ個人の同一性判定に使わない。

検証済み0件ではグラフを描かず「0件（取得確認済み）」とする。未取得や読込失敗を0件に置き換えない。プレイヤーごとの時系列や勝率のグラフは表示しない。

## データと保存

- 既存の集計JSONからプレイヤー一覧は復元できない。過去の一覧JSON（schemaVersion 1）は保持し、追加4項目を「未取得」と表示する。過去データに推定値や0を補わない。
- `--players` を明示した取得は、ランキングに表示された名前・公開プレイヤーID・国／地域・プラットフォームを読み、掲載アカウントの公開PLAYページから掲載キャラの今Actランクマッチ数も取得する。同一プレイヤーIDのプロフィールは取得回内で1回だけ読み、複数の掲載キャラへ対応する値を使う。
- 名前は2026-10-28に実画面で確認した、ランキング行内の `span[class*="ranking_name__"]` を読む。称号やコメントを名前に混ぜず、国／地域とプラットフォームも取得元の表示ラベルを保持する。
- 新しい一覧JSON（schemaVersion 2）は `players: [{ id, playerName, playerId, characterId, rank, masterRating, region, platform, rankedMatchCount }]` と出典・取得区間・Act・条件・検証情報を持つ。`id` は取得回内の連番、`playerId` は公開IDの数字文字列で、先頭ゼロも保持する。名前で同一人物を判定しない。
- `rankedMatchScope` に `actId`・`mode: "ranked"`・`collectionStartedAt`・`collectionEndedAt` を保存する。プロフィール取得区間を順位・MRの取得区間と分け、同じAct・掲載キャラ・ランクマッチであることを確認する。manifestはschemaVersion 1を維持し、集計と一覧の共通descriptorは順位・MRの取得区間で一致させる。
- 全掲載行の必須項目と対戦数を確認した場合だけ、`public/players/index.json` と `legend-*.json` を公開用に出力する。欠測・不明・別Actを0としない。実際に確認した0回は0として保存する。
- プロフィールURL・一時照合ハッシュ・認証情報は保存しない。表示名やラベルは文字列として扱い、HTMLとして実行しない。
- 公式Legend表示・末尾・先頭・重複・MR順・Actなどの既存検証、5秒の取得開始間隔、アクセス拒否やCAPTCHAでの停止条件を再利用する。完全取得の失敗を部分一覧や0件で代替しない。
- 通常の `data:collect-legend-analysis` は集計専用。日次workflowの一覧出力は明示的な設定で有効化し、最初は手動単発で確認する。

## Actionsでの単発確認と日次運用

既存の `Collect daily Legend analysis` を利用する。実行はmainのコード・GitHub hosted Windows・既存の保存認証に限定する。一覧を有効化すると、ランキングの確認後に掲載アカウントのプロフィールを巡回する。

取得開始間隔は5秒以上。一覧取得時の内部期限は120分、readerが開始するページ遷移とモード変更は合計2000回まで、異なるプロフィールは1000件まで。画像等を含む実HTTP通信全体の件数ではない。公式Legend表示を基準にするため500件で切らず、同率掲載も含める。上限を超えた場合は部分一覧を公開しない。Actionsの取得jobは一覧有効時130分、集計専用時20分で打ち切る。

1. mainへ反映後、手動実行の `include_players` を `true` にして単発取得する。初期値は `false`。この手動入力はその1回だけに適用される。
2. 取得・検証・Artifact・履歴保存とページ表示の成功を確認する。
3. 成功後にリポジトリ変数 `LEGEND_PLAYERS_DAILY_ENABLED` を文字列 `true` に設定すると、以後のscheduleで一覧も保存する。未設定または `true` 以外なら日次は集計専用のまま。

取得jobと履歴保存jobには、同一の厳密な真偽値を渡す。一覧を有効化したのにファイルがない、無効なのに一覧が含まれる、集計と一覧の取得回が一致しない場合はアップロードや保存を止める。

Artifactは検証した集計JSONと `public/players/index.json`・`public/players/legend-*.json` だけ。認証を受け取らない保存jobで両方を再検証し、既存の `codex/legend-analysis-history` ブランチへまとめて保存する。各データ種別は既存の厳密なvalidatorと不変履歴publisherを使い、両方を組み立ててから履歴ディレクトリを入れ替える。一覧を無効化した日の集計更新でも過去の一覧を保ち、取得失敗では失敗状況と以前の正常な一覧を保持する。

診断ログの `attemptFailures` に、全体の取り直し前の試行番号・段階・ページ番号・エラー分類・検証項目・再確認差分の分類を保存する。`humanVerification` はWAFヘッダーの確認有無・分類と可視DOMの人間認証検出結果を持ち、未観測と非検出を区別する。本文・認証値・個別プレイヤー値は診断ログに入れない。CAPTCHAやアクセス拒否の停止条件は維持する。

2026-10-31時点でv2はローカル実装。追加項目を含む実サイトの全件再取得、mainへのマージ・プッシュは未実施。

## 操作

```powershell
# このチェックアウトに既存の保存認証がある場合の単発取得
npm run data:collect-legend-players
# 表示された取得回の public/players を指定
npm run data:import-legend-players -- .local/legend-analysis-daily/captures/<取得回>/public/players
npm run validate:legend-players
npm run test:legend-analysis
npm run build
```

取り込み先は `public/data/legend-players/`。既存集計の取り込みと同じ、検証・不変の取得ID・作業フォルダーからの入れ替えを再利用する。一覧の取り込みに失敗しても以前の正常データを保つ。公開リポジトリへのプッシュやデプロイは別の操作。

ページの読込は共通の `usePublishedData` と `createPublishedDataFeed` を再利用し、起動時・表示中5分ごと・タブへ戻ったときに確認する。一覧の配信元は既存履歴ブランチの `public/players/`。そこに完全な検証済みデータがない間は同梱JSONを使う。ページを開く操作はBuckler取得を開始しない。

## 再利用

SF6の `LegendCharacterTable` のソートとアクセシビリティ、`table.css`、`StatisticsPanel`、取得記録・配信読込・不変履歴の検証を利用する。兄弟プロジェクトの一覧を参照し、SF6の既存テーブルを拡張する。

グラフ切替はランク分布ページのボタン操作、件数軸は `legendPlayerCountAxis`、文字幅は `chartTextWidth`、MR集計は `summarizeLegendMr` を再利用する。キャラ別縦棒の名前・横スクロールは `ExpectedMatchesChart`、棒の上の件数表示は `BalanceAdjustmentCountChart` の配置を参照する。順位グラフは `WinUsageScatterChart` のサイズ測定・選択操作と、兄弟 `arknights_2` の `OperatorPcaScatter` の点選択を参照する。既存scatterの割合軸やキャラID一意という前提は適用せず、順位・MR・取得回内行IDに対応した部品として分離する。
