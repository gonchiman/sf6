# レジェンド帯分析

`#legend-analysis` で、Bucklerのレジェンド掲載エントリーのキャラ構成とMR分布を表示する。

## 対象と指標

- 取得元は[マスターランキング](https://www.streetfighter.com/6/buckler/ja-jp/ranking/master)。今Act・キャラクター総合・全地域・全プラットフォーム・取得元の標準ユーザー条件を使う。
- 集計単位は**アカウント×掲載キャラ**。同一アカウントの別キャラも各1件とする。実人数や対戦回数ベースの使用率ではない。
- Legendの判定には公式の `rank37_l.png` を使う。2026-10-16に公式画像がLEGENDであることと、500行目を越える同順位にもこの表示が続くことを画面で確認した。行数や「500人」で打ち切らない。
- 最初の非Legend掲載を含むページまで取得し、Legendが連続する範囲を集計する。総合MRランキング全体の総数は、Legend構成比の分母には使わない。
- キャラ構成比はそのキャラの掲載数÷その回のLegend掲載総数。0件キャラは、公式キャラクターセレクトで確認した台帳に属するときだけ0として表示する。
- MR階級は50刻み、下限以上・上限未満。最小・第1四分位・中央値・第3四分位・最大・平均は個々のMRから計算する。分位点はR7方式、階級の中点からは推定しない。
- 現在の掲載集団の観測であり、同じ人物や固定したエントリーを継続追跡する統計ではない。構成比からキャラの絶対的な強弱や調整の因果効果を断定しない。

## 取得と検証

`scripts/collect-legend-analysis.ts` は既存の保存認証をメモリ内で再利用する。ログイン操作、認証の再保存、チャレンジ操作は行わない。

1. 固定条件のランキング1ページ目を確認する。
2. 先頭の掲載プロフィールの公開PLAYページで、可視のAct選択肢から今Actの固有番号を確認する。プロフィールのIDや成績は保存しない。
3. ランキングの公式キャラクターセレクトを開き、キャラID・キャラ表示名の台帳を確認する。ランダムは除外する。
4. 全Legend掲載をページ順に取得する。各ページの条件・Act選択・ページ番号・表示範囲・行数・MRと順位の順序・キャラID・Legend表示を検証する。
5. 同一アカウント×キャラの重複を、その取得内だけで共通のsalt付きハッシュを使って確認する。別キャラは重複にしない。重複行を削るだけで成功扱いにはしない。
6. Actを再確認し、末尾と先頭のページを再読して掲載行を照合する。取得中の不整合は有限回だけ全体を取り直す。未解決なら失敗とする。
7. 件数合計・MR階級合計・キャラ台帳・要約統計を厳密検証した集計JSONだけを出力する。

ページ遷移は最低5秒間隔。1取得のランキング読込上限は120回、全体の試行は最大2回、実行期限は15分。MASTER全体の総数増減だけでは失敗させない。Legend範囲の連続性・終端・先頭と末尾の掲載行は別に検証する。

要求先と応答先が一致するHTTP 5xxの一時エラーは、5秒以上待って1回だけ再試行する。認証要求・アクセス拒否・リクエスト制限・別URLへの転送では再試行しない。

実行レポートの`requestCount`はページ遷移の試行数。画像・スクリプトなどを含む総HTTPリクエスト数ではない。準備用のAct・キャラ一覧確認も別に行う。

取得には開始〜終了の時間幅がある。ページ間の更新をすべて検出できる同時点スナップショットではなく、その取得区間の観測値として表示する。必須項目の欠損・未知キャラ・認証切れ・メンテナンス・HTTPエラー・部分取得を0件で埋めない。

## 保存と前回比較

- 自動更新の読み込み元：公開履歴ブランチ `codex/legend-analysis-history` の `public/index.json` と取得回別の `legend-*.json`。ブラウザーからGitHub Rawの集計JSONを読み込む。
- 同梱データ：`public/data/legend-analysis/index.json` と取得回別の `legend-*.json`。公開履歴の一覧または最新取得の本体を読み込み・検証できない場合の代替に使う。
- 保存項目：出典・取得区間・生成日時・Act・条件・集計定義・確認済みキャラ台帳・掲載件数・キャラ別集計・MR階級と要約値・検証項目。
- プレイヤー名・プロフィールURL・個別ID・一時ハッシュ・Cookie・認証状態は配信用JSONへ入れない。
- 同Act・同条件・同定義・同掲載判定で、取得区間が重ならない直前の正常取得と比較する。件数差と構成比のポイント差を表示する。各回の分母はその回の掲載総数。
- Act切替・初回・比較条件不一致では差分を「—」にする。読込失敗は当回と前回を分離して再試行できる。
- 取得失敗は取得状況として残し、過去の正常データを維持する。正常な0件・未取得・検証待ち・取得失敗・ファイル読込失敗を区別する。
- 取り込みは全入力を検証してから作業フォルダーで組み立て、検証後に入れ替える。同じ取得IDの内容改変を拒否する。

## ページへの自動反映

- ページを開いたとき、表示中の5分ごと、非表示のタブから戻ったときに履歴の一覧を再確認する。一覧を永続キャッシュせず、取得回の本体は配信元・取得条件・公開版を含めたキーでキャッシュする。
- 最新の取得日を表示中なら、新しい正常取得へ自動で切り替える。過去の日付を選んでいる場合はその選択を保ち、前回比較も選択した取得に合わせる。
- 一覧と取得回の本体は同じ配信元から読む。検証済みの新しい本体を確認してから表示を更新する。通信失敗や不正なJSON、履歴の欠落・後退では、表示中の正常データを保ち、更新確認の失敗を表示する。
- 最初の読み込みで公開履歴を利用できない場合は同梱データを表示し、その状態を明示する。以後の自動確認または「更新を再確認」で公開履歴への復帰を試す。
- 日次取得が失敗しても、履歴に保存された正常取得と取得失敗状況を表示する。ページを開く操作がBucklerへの新規取得を起動することはない。認証情報はブラウザーへ渡さない。
- ローカル開発画面とGitHub Pagesで同じ仕組みを使う。GitHub Pagesでは、この実装をmainへ反映して一度デプロイした後は、集計履歴の追加だけで表示を更新できる。GitHub側のキャッシュや通信状況により反映まで遅れが生じる場合がある。

## ローカルでの操作

```powershell
npm run data:collect-legend-analysis
# 表示された保存先の public フォルダーを指定
npm run data:import-legend-analysis -- .local/legend-analysis-daily/captures/<取得回>/public
npm run test:legend-analysis
npm run build
```

収集用の保存認証は、従来のBuckler検証で本人が保存を許可したこのPCのDPAPI状態を使う。保存認証が失効している場合は新しいログインが必要。暗号化ファイルをGitHubへ送らない。

## 日次実行

`.github/workflows/legend-analysis-daily.yml` に毎日22:45 JST（UTC `45 13 * * *`）のscheduleと手動実行を定義する。**ローカル実装しただけではGitHub上で実行されない。mainへ反映した後、手動実行を検証する。** GitHub Actionsの開始時刻には遅れが生じ得る。

- 取得jobは読み取り権限だけを持ち、既存の `BUCKLER_WEEKLY_SESSION` を実行時に検証・環境変数から削除し、ブラウザーへは必要なOS環境だけを渡す。
- 認証はログイン済みかを確認して再利用する。ログインやロボット認証を自動で突破する仕組みではない。既存のランク分布用SecretがこのMR取得でも継続して使えるかは、実際の日次workflow実行で別途確認する。
- Artifactには検証した `public/index.json` と `public/legend-*.json` だけを含める。
- 保存jobは認証Secretを受け取らず、集計JSONだけを再検証し、独立したデータ専用ブランチ `codex/legend-analysis-history` の `public/` に履歴を追加する。初回にこのブランチを作成する。
- データ専用ブランチは公開リポジトリ内の集計履歴。アプリの公開・デプロイは行わない。既存の週次ランク分布workflowと履歴は変更しない。
- 日次保存後は、ページが公開履歴を読み直して自動反映する。通常の閲覧に手動importや毎回のアプリ再ビルドは不要。同梱データも更新したい場合は、データブランチまたはArtifactの `public/` を上記importに渡す。

1日1回は試行頻度。取得元の利用条件・更新状況と実測した取得時間・失敗率・リクエスト数を確認して調整する。プロフィール成績や戦歴の集計を追加する場合は取得量を別に見積もる。

## 初回の実取得確認

2026-10-16のローカル実行では、保存認証の読み取り、今Actと公式キャラ台帳の確認、ランキングの複数ページ読み取りまで確認した。巡回途中にHTTP 405が返り、全件の整合性確認を完了できなかったため、取得失敗として記録した。

その後の日次workflowの手動実行では、保存認証を再利用したランキングの読み取りと、取得失敗状況のArtifact・データ専用ブランチへの保存を確認した。[診断付きの実行](https://github.com/gonchiman/sf6/actions/runs/38916457975)ではHTTP 200・ログイン済みの一覧を読み取れていたが、2回目の巡回の12ページ目で集計の整合性検証が停止した。追加した詳細診断によるローカル実行では、同一アカウント×キャラの重複検出による停止も確認した。認証失敗と集計の整合性失敗は区別する。

行を読み取る途中の画面更新を混ぜないよう、条件・範囲・全行を同期的に値へ固定してから照合用ハッシュを計算する。ページ内重複や前ページの本文が残る状態は、有限の表示待機で解消しなければ採用しない。ランキングのページ切り替えは、固定条件の通常のURL読み込みを使う。

修正後の最終ローカル実行（2026-10-17 0:14〜0:18 JST）も正常取得は未完了。ランキング等の遷移試行41回・一覧の読取成功39回で、全体取り直し後の17ページ目にHTTP 405が返り停止した。部分集計や表示検証用の架空データは配信用データへ登録していない。このHTTP応答を、認証失効やデータの重複が原因だと断定しない。

2026-10-18に[日次workflowの成功](https://github.com/gonchiman/sf6/actions/runs/39050365749)を確認した。取得区間は同日1:40〜1:42 JST、Act 13の501掲載エントリー・32キャラ。既存の `legend-listed-v1` の全件検証を通過した集計JSONで、取得job・Artifact保存・履歴保存が成功した。成果物をローカルでも検証し、配信用データへ取り込んでキャラ構成とMR分布の表示を確認した。初回の正常取得は完了したが、過去のHTTP 405の原因が解消したことや今後の全実行の成功を保証するものではない。

## 再利用した実装

画面は既存の`StatisticsPanel`・条件選択・`DataLoadState`・`table.css`を利用する。MRグラフは`RankDistributionChart`のレスポンシブ計測・0起点・数値表の設計を参考にした専用実装。前身の`enemyStatistics`・`enemyDistributionComparison`を参考に、有効件数と分位点・比較時の共通階級を扱う純粋処理をSF6内に配置した。

認証・出力・履歴の検証方法は既存のBuckler保存認証とランク分布collector/importerを踏襲し、Legend固有のDOM・集計・検証を分離した。既存のLPランク型や35境界の集計をLegend用に変更していない。

自動反映でも既存のLegend manifest・取得回parserとdescriptor照合を再利用する。兄弟プロジェクトの`enemyAggregationData`（一覧の再取得と本体キャッシュの分離）と`gameDataClient`（配信元を固定した読み込み）を参考に、SF6内の`legendAnalysisFeed`と`legendAnalysisRefresh`へ実装する。
