# 共通ルールの運用

作業開始時に読む。`arknights_2` と `sf6` の共通原本は `gonchiman/project-rules` で管理し、このリポジトリでは `instructions/shared/` の同期コピーを使う。作業ごとの読み込み先はルートの `AGENTS.md` を参照する。

## 共通と固有の保存先

- `instructions/shared/` と `scripts/sync-project-rules.mjs` は共通原本の管理対象。直接編集せず、原本で改善をコミットしてから差分確認・同期する。
- このリポジトリの取得条件、統計の定義、配色ID、部品への参照、実装状況は `instructions/` の共通フォルダー外またはテーマごとの `docs/` に保存する。共通本文を複製して別管理しない。
- `project-rules.lock.json` は取り込んだ原本のコミットと各ファイルのハッシュを保持する。同期コピー・ツール・lockの変更を一緒にレビューし、コミットする。
- 普段の作業とCIの整合性確認は、ローカルのコピーとlockだけで行う。原本のクローンやネットワークは必要ない。

## 確認と更新

```sh
npm run rules:check
npm run rules:diff -- --source ../project-rules
npm run rules:sync -- --source ../project-rules
npm run rules:check
```

`../project-rules` は原本を兄弟フォルダーに置いた場合の例。別の場所では `--source` にそのチェックアウトを指定する。別PCで原本を更新・同期するときは `gh repo clone gonchiman/project-rules` などでクローンし、原本のコミットを確認してから使う。特定の版は `--ref` で指定する。

差分確認は書き込みを行わない。同期は共通コピーの手動変更・欠損や同期先の衝突を検出したら、書き込みを始めず停止する。強制上書きで解決せず、手元の変更を確認して原本または固有ルールへ反映してから再実行する。

同期中の `project-rules.sync.lock` は二重実行の防止と復元記録に使う。処理が止まって残った場合は所有プロセスと復元記録を確認し、無条件に削除しない。

原本を改善しても、他プロジェクトの変更も依頼されていなければ自動で同期・コミットしない。共通ルールの版とアプリの実装・公開は別に扱い、ルールを更新したことだけを理由に既存画面を一括変更しない。
